## Tightening a shared matcher ripples to every grant authored against its loose semantics

- **Tightening a shared MATCHER/predicate ripples to every GRANT authored against its loose semantics — the same blast-radius discipline, one axis over from data-shape refusals (earned 2026-08-18 (o), the §5.4 self-match).** Removing `MatchesPattern`'s bare-prefix self-match (`X/*` no longer matches bare `X`, restoring canonical §5.4) was a *correctness* fix on one function, but authorization is CHECKED through that function, so it silently invalidated every capability grant whose scope relied on the loose match. It 403'd `maintain-peer`/`status`/`reconnect` because `ext/network`'s handler grant listed `system/network/*` as its resource and depended on that covering the BARE `system/network` the ops actually target — seven tests red in a package the matcher fix never mentions. The producer-set of a data-shape refusal is "every place that MINTS the shape" (the rule above); the producer-set of a matcher-tightening is **every grant, default-connection-grant, and scope config whose include/exclude patterns were written against the OLD behavior**. Enforcement: when you tighten a shared matcher/canonicalizer/predicate, `git grep` the grant constructors (`CapabilityScope{`, `Resources:`, `Handlers:`, default-grant builders) for patterns that lean on the loosened case, and run the FULL suite — the authorization tests that move live nowhere near the matcher's own package. The tell you got it right: rust/py already carried the tight matcher, so their grants already list the bare path explicitly — a cross-impl divergence in the *permissive* direction is a grant you are about to have to make explicit. ## A value routed through a shared derivation is honored only where the input reaches it intact

- **A value routed through a shared derivation function is honored ONLY where the input reaches the function intact — a dispatch-time struct REBUILD that copies some fields and drops others silently defeats the function, and the unit suite is structurally blind to it because the unit calls the function with a full struct (candidate, first bite 2026-09-11 — my OWN wire vector caught it; the F68 `effective_targets` fix).** Landing `capability.EffectiveTargets` (§5.2, 0.8.2.20) as the single subject-derivation point for the authorizer (`CheckResourceScope`) and every handler (`hctx.ResourceSubject`/`ExtractResourcePath`) was unit-green, vet-clean, race-clean — and INERT on the wire, because `normalizeResourceTargets` (`core/protocol/dispatch.go`) rebuilt `types.ResourceTarget` as `&types.ResourceTarget{Targets: ...}`, dropping the caller's `Exclude`. So the handler's `hctx.Resource.Exclude` was always empty, `EffectiveTargets` skipped nothing, and the self-excluded (a) and case-D (b) WIRE vectors answered 200/403 where they must answer path_required / read-Q. Every unit test PASSed because they call `EffectiveTargets`/`ResourceSubject` directly with a fully-populated struct — the drop happens only on the dispatch path a unit never exercises. This is the exact wire-only sibling of the two-layer drift `effective_targets` was built to close: the fix needed a THIRD site (the dispatch normalizer) the design named only two. Enforcement: when you route a value through a shared function that reads a struct field, `git grep` every site that CONSTRUCTS or REBUILDS that struct on the dispatch/handler path (`normalize*`, cloners, `&types.X{...}` field-by-field copies) and confirm it preserves EVERY field the function reads — a field-dropping rebuild defeats the function silently; and prove the fix with a WIRE vector (positive AND negative), because a unit test handed a full struct cannot see a producer that drops the field. Same family as "Go-on-Go passes deceptively; the wire/cross-impl drive is the true signal," on the axis of a struct-rebuild that starves the shared function of its input. Teeth: `resource_effective.resource_effective_self_excluded_path_required` + `resource_effective_case_d_witness` (both mutation-verified RED against the exclude-dropping normalizer AND against a handler reading `Targets[0]`).

## A defense-in-depth panic on a path is a remote DoS unless every channel validates it

- **A defense-in-depth `panic`/assert guarding a path (or any value) is only defense-in-depth if that value is validated on EVERY channel that reaches it — a handler that derives a SECOND path from params is a channel the resource-target pre-validator does not cover, so the assert becomes a remote DoS (candidate, first bite 2026-09-11 — rust's panic-shape grep routed the class; the reachability was CONFIRMED, not assumed).** `core/store/namespaced.go:canonicalize` panicked on a malformed path under a comment asserting *"external input is validated at the dispatch layer before reaching any handler."* False: the dispatch pre-validator (`core/protocol/execute.go`) validates only `Resource.Targets`, and `system/tree:extract` (`paths[]`) and `:merge` (`target_prefix`+source-envelope bindings) hand a caller-controlled PARAMS path straight to the location index — so a control char or non-peer segment in params reached the assert and unwound the connection task, for ANY authenticated peer holding a normal grant (extract unconditionally; merge with a wildcard `put` grant). The tell it was reachable, not theoretical: a subagent traced the concatenation `fullPath := prefix + relPath` with `relPath` from unvalidated `extractReq.Paths` to `LocationIndex.Get` → panic, with the DispatcherLocationIndex confirmed to be a `NamespacedIndex`. **Two enforcement points. (1)** `git grep 'panic('` in any store/path/index/canonicalizer code and, for each hit, ask *can a caller-controlled value reach this?* — the answer is not "the dispatch layer validates it" unless you have confirmed the dispatch layer validates THIS channel; a params-carried path is a DISTINCT channel from the resource target and the resource-target pre-validator says nothing about it. **(2)** the fix is to make the boundary TOTAL (rust's exact "make the boundary function total, not an assert" shape, applied to go's store): a malformed path is untrusted input to REFUSE, not a programming error to assert on — reads fail closed to absent, writes return an error, the handler shapes the 400. Same family as "a control MUST fail closed on its own config" and rust's `qualify_path`-total fix; the new axis is *which channel carries the value the assert guards*. Teeth: `core/store.TestNamespacedIndex_TotalOverMalformedPaths` (boundary total, mutation-verified) + `core/tree.TestExtractMalformedPathIs400NotPanic` (handler 400, and a green run IS the no-panic proof).

## An unmatchable/sentinel value's safety is directional (fail-closed in include, fail-open in exclude)

- **An unmatchable/sentinel value's safety is DIRECTIONAL: fail-CLOSED in an include/allow position, fail-OPEN in an exclude/deny position — so a matcher that returns false for it silently WIDENS a grant when the pattern sits in an exclude, and the whole cohort shipped it (ratified 2026-09-11 — arch shipped the fail-open in 0.8.2.20 over rust's fail-closed reading, corrected it cohort-wide in 0.8.2.21 H1; go had it).** §5.4 canonicalizes `*/`/`./`/`../`-leading patterns to NEVER_MATCH, and `matches_pattern` returns false for it. In an `include` that is fail-closed (covers nothing → grants nothing). In an `exclude` it is fail-OPEN: carves out nothing → the grant is silently wider than its author wrote, with no error anywhere (a granter writing `exclude: ["*/secret"]` gets an exclusion that excludes nothing). go had exactly this: `isExcluded` ran the unmatchable exclude through `MatchesPattern` → false → not excluded → allow. **Two enforcement points, both required by the spec as TWO LAYERS because a single layer author-or-caller input can make vacuous is not a gate. (1) Evaluation:** an exclude/deny arm MUST treat an unmatchable pattern as matching EVERYTHING (deny), never defer to the matcher's false — `git grep` every exclude/deny-position use of the shared matcher (`isExcluded`, `matches_scope`, any `Exclude` loop) and confirm the unmatchable case is handled explicitly. **(2) Authoring/verify:** a capability any of whose scope patterns (include OR exclude) canonicalizes to the unmatchable value is INVALID `[MUST]` — refuse `400 invalid_path` at mint/delegate (§6.2) and treat as invalid at verify (§5.5), because the two readings (refuse vs honor-a-wider-grant) are **different authorization decisions on the same bytes across a peer boundary**. It is a MUST, not a MAY, for exactly that reason. Same family as "a control MUST fail closed on its own config" and rust's "make the boundary function total, not an assert," on the new axis of *which side of a set-membership test the unmatchable value sits on*. The discriminating test control is a WELL-FORMED exclude beside the malformed one (`/*/secret` denies `/{peer}/secret` but not `/{peer}/public`), or the row cannot tell a working exclusion from a grant that denies everything. Teeth: `core/capability.TestCheckResourceScopeUnmatchableExcludeExcludesEverything` (eval, mutation-verified) + `TestFirstUnmatchableScopePatternDetectsAllForms` (validity, all three forms). The wire-drivable vector `CORE-EXCLUDE-UNMATCHABLE-1` is keystone's per arch's assignment.

## PD-2 presented authority: root-not-leaf granter, and the confused-deputy oracle class (E1/E3/F70)

  > **RATIFIED 2026-09-10 — a new authorization ARM must be tested against the base gate it could BYPASS, or the cohort ships the bypass: F67, keystone caught it, and go+rust+py all had it.** PD-2's 0.8.2.17 presented arm said a target-minted credential's *"own four dimensions authorize the sub-dispatch"* while exempting the handler's `peers` scope by name. go implemented `presentedAuthorizes` as a STANDALONE authorizer — a valid presented cap `return`s authorized at `core/protocol/outbound_authz.go:46-50` BEFORE the ambient handler-grant check (`:59-72`) ever runs — i.e. the credential became the whole gate. That is the confused deputy with the ceiling removed: the credential arrives as a caller-supplied param (the scaffold's `dispatch-outbound`), so a caller holding any `T→P` cap steers ANY handler on P past its own grant. **All three ground-up impls implemented the identical bypass** (rust `connection.rs:3545-3557`, py `peer.py:3635-3650`), two with design prose defending it — a spec-licensed defect the whole cohort took. `entity-core-keystone` caught it by reconciling the AUTHORITY MODEL (§3.6b Level-1/Level-2), not the arm's prose; 0.8.2.19 (`4242b18`, E1) fixed it: **the handler grant is the gate on all four dimensions (§6.8); a valid target-minted credential relaxes Dimension 4 (peers) ONLY.** The D1 root-granter reading in the note above STANDS; what was wrong is `presentedAuthorizes` authorizing *alone* — "the leaf granter is then used only for PR-8 canonicalization in the coverage step" described the bypass, now corrected. **Three enforcement points, each a discipline we already held, unapplied: (1)** when you add an authorization ARM (a second way to authorize a dispatch), the mandatory teeth are the COMPOSE-vs-BYPASS discriminator — a case where the new arm's credential is VALID but the base gate (the handler grant) does NOT cover; assert REFUSE (compose), because the bypass form authorizes it. go's probe and unit test had only {credential+covering-grant → succeed} and {no-credential → refuse}, the exact two vectors that cannot see a bypass (arch's F63; and verbatim our own "both arms or it does not discriminate" / "the arm you do not exercise ships wrong" / "carry the teeth" family, now on the multi-authority-composition axis). **(2)** a two-half positive MUST ("the decision is made ON X, never on Y") is not satisfied by answering the negative half — §6.8's "made on the executing handler's grant" is unconditional; go answered only "a credential isn't the propagated caller_cap" and never gated on the handler grant.
