# Compute Error Semantics

How `compute/error` behaves across the two in-language representations and every consuming site. Read before touching the compute evaluator or its error paths.

_Moved verbatim from `AGENTS.md` during the 2026-09 memory split; content unchanged. Find an entry by its symptom._

---

## A compute/error has two in-language forms — cover both, at every consuming site and crossing

- **A `compute/error` has TWO in-language forms — cover both, or you have 0% coverage of one.** A minted error is a `*ComputeError` (a Go error, auto-propagating via `if err != nil`); a value-form error is an `entity.Entity{Type: compute/error}` reached by SA-1 (a literal, or a `compute/lookup/hash` resolving to a stored error) with a nil Go-error. `is_error` (§4.1, kind-based) unifies them, but ONLY where it is applied — so every value-consuming site must go through `evalOperand` (Evaluate + is_error), and every crossing (handler F10, reactive `result_path`, **SA-9 `store`**) must recognize both. **Earned 2026-08-16, measured:** the §2131 short-circuit was missing for the value form at five sites (arithmetic masked it as `type_mismatch`; compare/if/field didn't short-circuit; the reactive crossing wrote it verbatim — a §2.4 divergence). It was invisible because **every error-path test minted its error the same way** (a failing op / an unresolvable-hash lookup → the `*ComputeError` form) — 100% coverage of one representation, 0% of the other. py hit the identical blind spot (~300 tests). **Enforcement: an error-path test asserts BOTH forms** — a failing op AND a `compute/error` literal / a lookup onto a stored error — at each consumer (`TestValueFormErrorShortCircuits`, `TestReactiveErrorCrossingIsCodeOnly`, `TestStoreErrorCrossingIsCodeOnly`). Whenever a value type has two internal representations, a test that exercises one has not touched the other.
  > **Same-session addendum — the crossing list is itself a surface I under-enumerated.** The 877edf5 close-out fixed the `result_path` crossing and named it, but **§2.4 has TWO write-site crossings — `result_path` AND SA-9 `store`** — and the store crossing had the identical gap: the value form hit `materialize()` (which rejects a `compute/error` post-v3.23) → an *internal* error, wrote nothing; the minted form propagated instead of writing. Testing one write site was 0% coverage of the other — the same discipline biting **one level up**, on the *set of surfaces* rather than the *set of forms*. **No new discipline earned** (the existing two-representation rule applied to a surface I'd missed, not a novel invariant — per the close-out floor); the enforcement is completed: **enumerate every §2.4 crossing, not "the crossing."** The check is a grep of the rule's own surfaces — `git grep 'materializes where.*written\|SA-9 .store' ../entity-system-architecture/specs/extensions/EXTENSION-COMPUTE.md` lists both write sites; the test set must cover each. Fixed in `builtinStore` (both forms → `ToMaterializedEntity`, code-only); the write-vs-short-circuit reading it forced is routed (`docs/validation/spec-issues/2026-08-16-b-*`).
  > **Addendum 2026-08-21 (rust + py caught it) — a SHARED consumed-operand RESOLVER using bare `Evaluate` masks the short-circuit for BOTH forms, and a three-way corpus LOCK does not cover it (no new discipline — the existing "every value-consuming site goes through `evalOperand`" rule, with the enforcement sweep it lacked).** `resolveCollection` (the `collection` operand of map/filter/fold/assoc/group-by) called bare `Evaluate` then type-asserted `[]interface{}`, so a value-form `compute/error` operand fell through to `type_mismatch` — the §7.2 consumed-position short-circuit was missing entirely (not a two-representation split; a total miss at that operand). `concat` carried the same slip one level down (its per-sub-collection `c.([]interface{})` type_mismatched an error sub-collection, where §7.2 makes each sub-collection consumed→short-circuit — distinct from an error ELEMENT, which is CONTAINED, CV-5). **The go compute corpus LOCKED 352/352 three-way (go↔rust, go↔py) with the bug LIVE**, because no vector placed an error in the collection operand — py's "the two readings agree everywhere your fixtures live" law, with the corpus AS the fixture set: a LOCK proves agreement only on inputs the corpus contains. Two enforcement points, both grep-able: **(1)** `git grep 'Evaluate(' ext/compute` for any resolved operand that is then **type-asserted** — a consumed operand resolved with bare `Evaluate` instead of `evalOperand` is the shape (index/length already use `evalOperand`; the collection resolver did not); **(2)** the corpus discriminator for a consumed operand is an error IN that operand position — enumerate every consumed operand a primitive has (collection, index, key, each sub-collection) and seed an error-in-each, not only the positions already covered. Fixed: `resolveCollection` → `evalOperand`; `builtinConcat` short-circuits an error sub-collection; teeth `TestCollectionOperandErrorShortCircuits` (5 ops × both forms) + `TestConcatSubCollectionErrorShortCircuits`; corpus CV-7a/b/c (352→355, SHA re-pinned `86bc5e8a`). The go-on-go corpus passing was never the signal — the cross-impl catch was (this repo's standing "Go-on-Go passes deceptively, the cross-impl FAIL is the true signal," here on the axis of *corpus coverage* rather than a shared helper).
  > **Corpus addendum (the three-way run, `docs/validation/reports/2026-08-16-c-*`) — two existing disciplines, two new surfaces, both caught by a control, no new rule minted.** (1) The corpus *harness* had the same two-representation split: `boundaryOf` reduced a value-form `compute/error` result to entity-kind while `evalVector` reduced a minted one to error-kind, so the reduction disagreed with the wire (F10) on exactly the store vectors. **The route-A-vs-route-B control (go in-process vs go driven over its own wire) is what caught it** — run that control before trusting any cross-impl lock; a spurious inproc-vs-wire divergence is a harness-reduction bug, not a peer bug. Fixed: a `compute/error` result reduces to error-kind everywhere. (2) **To gate a property of a WRITTEN entity, read the written entity — not the eval result.** §2.4 code-only is a property of the *stored* bytes; the eval result cannot show it (a `compute/error` result reduces to error-kind, keyed on `code` and blind to `message`, and over the wire F10 re-wraps it with a fresh message so it is not even the stored bytes). The store vectors carry `Vector.BoundaryPath`: the boundary is the content hash of the entity at the store path, read out of band (in-process location index; wire `TreeGet`). This is "conformance-green ≠ correct if the test asserts the wrong thing" (ADR-0012), and the fix is to assert on the right artifact — the written entity — after which the gate went from a false LOCK (codes agreed) to a true RED: go writes code-only, rust/py write nothing (propagate). **Do not vote the correct impl wrong because the cohort agrees** — cross-bless labels the store divergence "go's bug (one-differs)" because rust+py agree, but §2.4 makes go correct; the spec arbitrates (routed: spec-issue `2026-08-16-b`).
