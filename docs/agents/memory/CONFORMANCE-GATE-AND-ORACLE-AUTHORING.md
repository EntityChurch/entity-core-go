## A refuse-this-shape rule ripples to every producer — fixtures, the oracle, the arming flags; and how to run the release gate to a true exit 0

- **A new MUST-REFUSE on a data shape ripples to every PRODUCER of that shape — the oracle and the harness included, and `go test` alone will not catch it (earned 2026-08-18, CAP D11/D12).** Landing "reject a policy with null default_ttl" broke, silently, three producers of the now-invalid shape that the unit suite is blind to: the `registry_issuer` conformance checks that seed `{Mode: Open}` with no ttl (they'd have gone RED against an armed peer), `set_issuer_policy_replaces_whole` (it *asserted* the field could be cleared — now forbidden), and `validate-complete.sh`'s `--issuer-policy-mode open` arming with no `--issuer-policy-default-ttl` (the armed registry would fail its own register vectors at D12). This is the sibling of "enumerate every surface a rule names" on a different axis: a refusal rule's blast radius is every place that MINTS or SEEDS the refused shape — impl mint paths, test fixtures, **the oracle's own positive-path checks, and the peer-arming flags** — plus a matching negative conformance check. Enforcement: when you add a refuse-this-shape rule, `git grep` every constructor of the shape (here `IssuerPolicyData{`, the arming flags, `setIssuerPolicy`), and run the live category against an armed peer — a green `go test` is not evidence the wire suite still passes.
  > **Same-session addendum, but it bit again (2026-08-18 (c), earned — py caught it, not us).** The rule above failed twice over in one commit-family: (1) its producer list — "impl mint paths, test fixtures, the oracle's positive-path checks, the peer-arming flags" — **omitted the conformance FIXTURE GENERATOR** (`cmd/peerissued-fixtures`), a `main` package with a `-wire` self-verify that is invisible to BOTH `go test` and a raw `validate-peer` run; d948b4f's F2/D3 (peer-issued binding MUST carry a non-null ttl) made the generator refuse its own RESOLVE-1/PRECEDE-1 output, so `validate-complete.sh` aborted at step one for **every seat** and no impl could produce a conformance number. (2) The sweep was scoped to the *same-session* shape (D11/D12 policy) and never re-run against the **prior-session** refuse-rule in the same family (d948b4f F2/D3 binding), which had the identical blast radius unswept. The completed rule: a refuse-this-shape sweep's producer set includes **every generator that MINTS the shape for conformance, the fixture generators included** (`git grep` the shape's constructor across `cmd/*fixtures*` too, not just impl + harness), and landing a *new* refuse-rule obliges re-sweeping **every prior refuse-rule on a related shape** — a refusal family's producers accumulate across sessions. **Enforcement, hard: a close-out that claims "green" MUST have run `scripts/validate-complete.sh` to exit 0 and say so — `go test` green is not the release gate, and a close-out that names "full suite green" without naming the suite is how two gate failures (this fixture blocker AND pass-0b register drift) shipped under one.** (This is ADR-0012 green≠release, with the specific bite that the gate lives in a `main` self-verify and a static register pass, neither of which the unit runner touches.)
  > **Sharpened 2026-08-22 — read the gate's exit FROM the gate, never through a pipe: `validate-complete.sh | tail` returns TAIL's 0 and masks the gate's own exit 1 (earned; a prior close-out shipped on the masked form).** The rule above says a close-out claiming "green" MUST run `validate-complete.sh` to exit 0 — but running it as `./scripts/validate-complete.sh 2>&1 | tail` reports `[exited with code 0]` from **tail**, not the script, because a bash pipeline without `pipefail` takes the last command's status. Line 532 of the script exits 0 only if all six `RC*` are 0; the human-readable tell is its own summary line — `PASS 0 exit 0 · … · PASS 1 exit 1 · …` — where **any nonzero `PASS k exit` means the gate FAILED**, whatever a piped `[exited with code 0]` says. This bit twice: this session's first run printed `[exited with code 0]` over a real exit 1, and the immediately-prior go close-out claimed *"exit 0 on all six passes"* while the transcript's own summary read `PASS 1 exit 1` — the masked exit shipped as a green sign-off. **Enforcement: run the gate UNPIPED to a file and read `$?` (`./scripts/validate-complete.sh >log 2>&1; echo $?`), or `set -o pipefail`; and a close-out that quotes "exit 0" must quote the six per-pass `exit N` values, not a pipeline's status.** Same family as "presence is not validity" (a green `plan` that made no call) — here a green *exit* that was never the gate's. The nonzero this session was itself instructive but NOT a code defect: the six `peer_issued` FAILs were a sibling's leftover peer squatting `PI_PORT` 9401 (core-py's documented hazard — re-run with `PI_PORT=<free>`), a cross-session environmental collision, not a go regression; re-run clean on 9411. **No new discipline in the C-1..C-4 corpus work itself** — the de-version fold RE-APPLIED the standing "a Skip-on-missing-file guard is only a guard if its path is live" rule (the PASS 0 `[ -d …/v767 ]` guard and `corpus.Check()`'s `ErrAbsent` both went quiet, exactly as predicted, when arch deleted `v767/`), recorded per the close-out floor; the only rule earned is the pipe-masks-exit one above.
  > **Third manifestation 2026-09-06 — pass 0b flips from a SIBLING'S spec-move alone, so a green go-code diff is NOT evidence the gate still exits 0 (py caught it; no new discipline, the enforcement is the same "run the gate unpiped to a true exit 0").** The cycle-5 close-out (`2026-09-05-b`) claimed "exit 0 all six passes" and had NOT been run to a true exit 0: pass 0b (the static conformance register, no peer) was exiting 1 on `registry.v16_ttl_ceiling_reread [was PARTIAL]` — a baseline entry that stopped applying because arch's REGISTRY v1.17/v1.18 citations began resolving, flipping the check PARTIAL → RESOLVED **with zero change to go's tree**. The baseline was last written cycle-2 `be35f90`; four go commits landed after it touching only tree/content, all unit-green, all vet-clean — and pass 0b was red the whole time, invisible to every go-scoped signal because the input that moved was a *spec repo*. The tell: pass 0b reads the register against a committed baseline, and the register resolves citations against `../entity-core-protocol` and `../entity-system-architecture` — so **any arch spec bump can flip a citation's resolution and drift the baseline without a single go byte changing.** Re-pinned (`go run ./cmd/conformance-register -write-baseline`, one line removed — a gain, not a regression), pass 0b → exit 0, full gate re-run unpiped on free ports to a true `PASS 0..4 exit 0`. **Enforcement (unchanged, just re-stated with the new trigger): after any arch spec move — and ALWAYS before a close-out — run `go run ./cmd/conformance-register -check` (or the whole gate unpiped) and read its own exit; a green `go test`/`go vet`/unit suite is silent on a pass-0b baseline drift, because the drift's cause lives in a sibling repo.**
  > **Sharpened again 2026-09-04 — the http-poll port collision is WORSE than the PI_PORT one, because its FALSE FAILs are indistinguishable from a real conformance defect, and the peer FAIL-OPENs on its own bind failure (candidate — the pre-flight guard is the enforcement point; cost a full bisect to attribute).** The 9401 hazard above produced `peer_issued` FAILs recognizable as a posture artifact. A leftover peer squatting `POLL_PORT` (9451, the `--http-poll-addr` listener) is nastier: `entity-peer` logs `WARNING: http-poll listener: … address already in use` and CONTINUES with **no content server**, so `serving_mode` 404s EVERY in-scope serve — ~23 checks — and the gate scores them as conformance FAILs that look exactly like a real serving defect. This session's go gate read `PASS 1 exit 1` with 23 `serving_mode` FAILs on a clean tree; only a `git stash` bisect (clean `c14a1d3` reproduced identically → not my diff) plus tracing the peer log to the bind WARNING (A1, trace the value — the tell was `content_get_in_scope_status 404, want 200` while `pass 2`'s namespace-scoped serving PASSed) attributed it. **The peer's warn-and-continue is a fail-open on its own configuration (the "a control MUST fail closed on its own config" discipline, applied to the serving listener surface); the gate must fail closed for it.** Enforcement, landed: `validate-complete.sh` now PRE-flights `POLL_PORT` and `POLL_PORT+1` (a bare `/dev/tcp` connect BEFORE the peer starts — a squatted port IS listening, so an *after*-start liveness probe cannot tell the target's own listener from the squatter's) and aborts exit 2 with the free-port re-run command rather than emitting false FAILs. Two sub-lessons: (1) run the gate on free ports on any box that has run peers this session (`POLL_PORT=<free> PI_PORT=<free>`), and never label a `serving_mode` FAIL a defect without checking the target log for the bind WARNING; (2) a bash gotcha caught building the guard — `exec 3>&- 2>/dev/null` redirects the SHELL's stderr to `/dev/null` for good (an `exec` with a redirection applies it to the current shell), which silently swallowed the abort message; close an fd with a bare `exec 3>&-`. **Re-application of "fail closed on own config," not a novel discipline** — recorded because the enforcement (pre-flight port guard) is concrete and the false-FAIL-vs-real-defect indistinguishability is the new, sharper bite.
  > **Completion on the CHECK axis (2026-08-19, §4.3 set-resolver-config close-out — no new discipline, recorded per the floor).** The producer-sweep rule above is written for a refuse-*shape*; the same blast-radius holds one axis over, for landing a new *validate-peer check*. Adding `v15_dispatch_config_refused` / `v16_ttl_ceiling_reread` was `go test`-green and `validate-peer -category registry`-green, and STILL failed the gate at **pass 0b** — the static conformance-register (`cmd/conformance-register/baseline.json`) flags any check whose citation is newly unresolved, and a new check is by definition newly-present. So a new check's producer surfaces are: the **type-count guards** (`core/types/types_test.go`) when it adds a type, and the **conformance-register baseline** (re-pin with `go run ./cmd/conformance-register -write-baseline` once the citation is confirmed grounded) — both static gates a green `go test` and even a green single-category `validate-peer` run do not touch. This is the same "name the suite, run `validate-complete.sh` to exit 0" enforcement, with the bite that the two gates a new check trips are **passes 0 and 0b**, upstream of any peer.

## Scheduling races are invisible on a multi-core box — run the suite starved

- **A scheduling race is invisible on a multi-core box — the gate must run the suite STARVED (`make test-starved`, GOMAXPROCS=1, repeated), because `make race` stays green on a lost UPDATE (candidate, first bite 2026-08-23, `fb6d461`; browser-rust's release gate surfaced it, and only on a loaded machine).** `ext/publishedroot`'s undebounced publisher spawned one goroutine per tracked-root advance, each carrying a CAPTURED root hash; under contention those reorder and a late goroutine holding an OLD root could publish it LAST, stranding the published root behind the tracked root — a §6.5.6 convergence FAILURE. It passed `make test`, `make race` (it is not a data race, so the detector is green on it), all 45 curated commits, a standalone published-tree run, and a fresh clone — every one on an unstarved `--cpus=8` box, where async goroutines schedule in near-order and it converges every time. It failed exactly once, on a loaded machine during a gate run. The measured tell was `seq > writes` with `converged=false`: the work was done, the WRONG root landed last (a lost update, not the "dropped tail / lost wakeup" the test's own message theorized — trace the value, A1). **Two enforcement points, both landed: (1)** the specific regression is pinned deterministically by `TestOnTreeChangeRecordsNewestInSlot` (asserts the coalescing slot holds the NEWEST advance and the drain publishes it — 100%, runs in plain `make test` on any box); **(2)** the general class is netted by `make test-starved` — `GOMAXPROCS=1 go test -count=N` across all modules, the lever that reproduces this on demand (~3/8 at count=1 pre-fix). Run it as a release-gate step ALONGSIDE `make race` and `validate-complete.sh`; the two detectors are orthogonal — starvation exposes reorder-dependent logic races, the detector exposes memory races, and neither sees the other's bug. When you add async coalescing/debounce/hook-fanout code, add a deterministic newest-wins/convergence test AND lean on `test-starved`; a green multi-core suite is not evidence a scheduling race is absent, it is evidence the scheduler hid it.
  > **Gate-step note (2026-09-17): `make test-starved` can fail on this box with `chdir /src/ext: permission denied` — a podman rootless mount-permission artifact of the CONTAINER target's per-module `cd`, NOT a build failure, and its tell is a contradiction (a log ending `make: *** Error 1` beside a masked `exit 0`, or `[build failed]` with a `permission denied` line above it, not a compile error). When you see it, DON'T chase it as code: run the detector host-native — `GOMAXPROCS=1 go test -count=3 ./core/... ./ext/... ./cmd/...` — which is what the target runs, minus the container. Same "read the actual error/value, not the summary or the exit" family as the pipe-masks-exit rule; recorded because a container FS artifact reads exactly like a code build failure and the next seat will hit it. (No novel discipline; this whole 2026-09-17 session was a batch of workbench-routed fixes — rows 2/3/6/7/8/10/11/12/13/15/16/17/21 — each re-applying existing disciplines, verified by the routing party's own repros run against this tree via their `replace` directives, with the gate/race/starved all green.)

## An async-on-contention defer creates a stale-read hazard for synchronous consumers

- **An async-on-contention DEFER creates a stale-READ hazard for every synchronous consumer of the state it defers — a distinct shape from the lost-UPDATE above, and one that GOMAXPROCS=1 starvation HIDES because it needs real parallelism (ratified 2026-08-30 — second bite of the `go apply(...)`-behind-a-`TryLock` class; workbench-go's burst reproducer surfaced it, ten days after it was written).** `core/tree.RootTracker.applyEventWithDepth` spawns the incremental root apply to a goroutine when the per-prefix lock is contended and returns before it lands, so `OnTreeChange` reports done while the cached `system/tree/root/{prefix}` still lags the live index. The AutoVersioner runs strictly AFTER the tracker on the same event *"so the tracked root is settled before we read it"* — but the defer breaks exactly that invariant: `fire()` read `tracker.Root()`, got a root missing the triggering (last-of-burst) write, built a deficient `versionRoot`, and the dedup check silently no-op'd the emit. Terminal, because a burst's last write has no next event — the *"symmetric last-burst-write loss."* Traced, not theorized (A1): under load with `ENTITY_AV_TRACE`, the failing run printed `[root-tracker] ASYNC-SPAWN … path=…/a-4.md` for the exact lost path, then `fire … dedup … no emit` — **zero CAS retries, zero no-tracked-root**, refuting the source comment that credited the CAS loop with closing this. It was invisible three ways the publishedroot bug was too (`make test`, `make race`, a fresh clone) PLUS one more that is the new teeth: **`make test-starved` (GOMAXPROCS=1) actively SUPPRESSES it** — with one runnable goroutine the spawned apply drains before `fire()` reads, so the settle-race never opens. Starvation nets the lost-UPDATE reorder; only real parallelism nets this stale-READ. **Fix + enforcement, both landed:** the tracker counts in-flight async applies per prefix and exposes `CurrentRoot`, which recomputes from the live index (authoritative, monotonic under a write-only burst → cannot regress or phantom-delete) whenever an apply is pending and keeps the O(1) cached-root adoption otherwise; `fire()` reads through `CurrentRoot`. Teeth: `core/tree.TestRootTracker_CurrentRootReflectsPendingAsyncApply` is DETERMINISTIC (holds the prefix mutex to force the defer, asserts `CurrentRoot` ≠ the lagging `Root`; mutation-verified RED when `CurrentRoot` delegates to `Root`), and `ext/revision.TestAutoVersion_CapturesEveryWriteUnderConcurrentBurst` is the parallelism net (RED on iter 0 pre-fix under `-race`). **Enforcement, general: when you add an async-on-contention path (`go work(...)` behind a failed `TryLock`), `git grep` every reader of the state it defers and confirm each is safe under the lag — a read-through that recomputes, or a pending-guard; a synchronous consumer that trusts "the hook ran" reads stale.** And add a DETERMINISTIC forced-interleave test (hold the lock, assert the read-through), because neither `-race` nor `test-starved` will catch a parallelism-gated stale read — the third detector this repo now owns. (Same finding also flags `ext/publishedroot/publisher.go`'s `tracker.Root` read as sharing the shape — reported to meta, not fixed here: it republishes on later events so it is not terminal.)

## A conditional assertion inside a check can silently no-op

- **A conditional assertion inside a check can silently no-op, and the summary PASS row cannot tell you it ran (ratified 2026-08-17 — a peer corrected around it).** `request_ttl_zero_and_overflow`'s no-ceiling probe fires only when the connection cap is nil-expiry, and the CAP-6 `ingest_rejects_unrepresentable_expiry` control runs only if the round-tripped normal-expiry token is honored — a skipped branch and an exercised one both print `PASS`. core-rust, validating the `(u)` check, *"checked the check's own message rather than the PASS row"* to see whether the branch ran, and said so. **Enforcement, both halves: (1) a conditional probe MUST report in its own PASS message whether the conditional branch executed** (as these two do: `"; no-ceiling overflow minted NO expiry…"`, and the control's honored-first gate that otherwise `SkipCheck`s), so a no-op degrades to a visible SKIP, never a silent PASS; **(2) verifying a check against a sibling, read the per-check MESSAGE, not the summary PASS/row-count.** Same family as ADR-0012 (green ≠ correct if the assertion didn't fire).

## When a check cannot be teeth-tested against a failing peer, carry the teeth in the check

- **When an oracle check cannot be teeth-tested against a failing peer, carry the teeth IN the check (2026-08-17).** The usual proof — run the check against a pre-fix commit and watch it go RED — is blocked when no failing peer is buildable: go never had the defect, and the git boundary forbids checking out a sibling's pre-fix commit (`entity-core-{py,rust}`). The CAP-6 ingest check instead embeds a **negative control**: a round-tripped *normal*-expiry token must be **honored first**, proving the construction reaches the expiry check, so a refusal of the hostile variants is attributable to the expiry rather than to a corrupted granter/chain; if the control is refused the check **SKIPs, not PASSes**. A hostile-input check whose valid-input control is never asserted is a candidate false-pass. (This is ADR-0012's mutation-has-teeth applied to a wire check — not a new invariant, a new place to apply it.)

## A byte-fidelity round-trip check is blind on three axes

- **A byte-FIDELITY round-trip check authored over a peer's OWN codec is blind on THREE axes at once, each of which independently makes a decode→re-encode the IDENTITY, so the check passes with the fidelity bug fully live — the discriminating fixture is bytes the codec cannot author, staged into a FRESH entity, spliced RAW (candidate, first bite 2026-09-15, core-rust found it in their tree and asked why our round-trip check missed).** core-rust's `handle_merge` rebuilt each `source_envelope` entity's data from a decoded `ciborium::Value` (which cannot hold raw bytes), losing any byte a canonical encoder would not author; the ingested binding then resolved to nothing while merge reported 200 applied. `tree_operations.roundtrip_verify_entity` — the right check in the right place — missed on three axes: **(1) canonical fixture** — an `ecf.Encode`-authored entity re-encodes to itself, so the round-trip is the identity; **(2) same-peer copy** — extract-and-merge into the same peer that already holds the entity under its true hash from `put_entity`, so the binding resolves from the prior copy even if merge stored a re-encoded one elsewhere; **(3) harness re-encode** — the harness built `source_envelope` through `interface{}`/`ecf.Encode`, canonicalizing the non-canonical leaf BEFORE the peer saw it. Measured, not argued: with a lossy re-encode injected into go's `handleMerge`, `roundtrip_verify_entity` stayed **PASS** while the new check went **FAIL (404)** on the same peer — the three axes are real and this fixture defeats them. go itself is immune by construction (`Data` is `cbor.RawMessage`; `EncodeHashable` embeds it verbatim; `MemoryContentStore.Put` recomputes the hash and refuses a mismatch — driven, not read), so the mutation is how the check's teeth are proven (a sibling's pre-fix commit is out of reach across the git boundary). Enforcement: a fidelity round-trip oracle uses a **non-canonical CBOR fixture** (`0xA1 0x61 0x76 0x18 0x01` — `{"v":1}` with `1` non-minimal; valid, no encoder authors it), on a **fresh entity the target has never held** (its only route into the store is the ingest under test), **raw-spliced** into the request (never round-tripped through `interface{}`/`ecf.Encode`, or the harness launders it), with a **canonical positive control that SKIPs-not-FAILs** if it does not itself round-trip (carry-the-teeth: else a non-canonical failure is unattributable). This is the corpus-coverage law ("a LOCK proves agreement only on inputs the corpus contains") + carry-the-teeth, on the specific axis of byte-fidelity round-trips — recorded because the three named axes are concrete and each must be defeated. Teeth: `cmd/internal/validate.merge_noncanonical_byte_fidelity` (`TREE §5.2, V7 §1.8`), mutation-verified RED against the injected lossy re-encode. Owed: the 3-way drive (rust post-`23513a0`, py). **Companion, no new discipline (the §1.8 sweep, 0.8.2.23, reaching a surface it did not name):** the merge `source_envelope` rides inside `params.data`, so its nested `included` map bypasses `Envelope.ValidateAll` — go now runs `VerifyIncludedKeyBinding(env.Included)` before ingest and refuses a failed `Store.Put` (was silently skipped, leaving a binding resolving to nothing at 200/applied). Enforcement: `git grep` every ingest of a wire-supplied `included` map that does NOT pass the receive boundary and bind its keys there too. Teeth: `core/tree.TestMergeSourceEnvelopeRejectsMisKeyedInclude` (mutation-verified). Code slot (`invalid_params` vs `hash_mismatch`) + cohort MUST routed upstream to the architecture seat.

## A state-independent MUST gets driven in only one state cohort-wide

- **A wire probe reaches a STATE-INDEPENDENT `[MUST]` only in the cheap-to-reach state, so an "in any state" clause is driven in exactly ONE state cohort-wide and no cross-impl run catches a regression on the arm nobody dials into — a probe DIALS IN, and reaching the expensive state (established, mid-handshake) is written as SETUP rather than as a state under test (candidate, py earned it 2026-09-02).** §4.7 row 10 (an unknown connect op → `400 invalid_request`) is "in any state," but every seat's `connect_unknown_operation` probe sends the unknown op on a FRESH connection, so the established arm went untested in all three harnesses; py's established boundary was actually wrong there (it answered `409` for the connection's STATE when the defect was the operation's NAME), and no cohort run could have said so because the cohort never drove that arm. go was already correct (`execute.go`: the unknown-op switch runs AHEAD of the state branch), so **this bit go's COVERAGE, not its behavior** — hence candidate, not ratified here. Enforcement: for a state-independent MUST, drive it in the EXPENSIVE state too and carry an in-probe control that the expensive-state branch still discriminates (here `connect_unknown_operation_established` sends `frobnicate` on an established connection → `400`, with a control that a `hello` in the same state → `409 connection_already_established`; if the control does not hold the branch is degenerate and the check WARNs rather than PASSes). Same family as carry-the-teeth: the arm you do not exercise is the arm that ships wrong. Teeth: `core/protocol.TestFold0902_UnknownConnectOperationIsInvalidRequestInAnyState` (mutation-verified — moving the unknown-op switch below the state branch reddens step 1). A related applicability control landed the same session: `connect_ping_before_hello`'s "peer must serve ping" caveat is now ASSERTED (`pingServedOnceEstablished`) instead of prose, so a peer that does not serve ping SKIPs the row rather than the `409` quietly failing a peer that conformantly answers `400`.

## An impl-agnostic oracle is mutation-verified only on the seat we mutated

- **An impl-agnostic oracle check we author is mutation-verified ONLY on the seat we mutated — on every other seat it is an unarmed CLAIM, and a spec-field oracle makes it PORTABLE, not ARMED (candidate, first bite 2026-08-31, py caught it).** We shipped `auto_version.burst_convergence_no_capture_loss` reading a spec field (REVISION §6.1 `status.pending`), verified its teeth honestly by reverting go's fix and watching it go RED, and reported it impl-agnostic. It was — and it was **blind on two of the three seats it was built to run against.** `pending` is computed only `if !headVal.IsZero()` (`ext/revision/status.go`, and the same guard rides every impl), so a peer that captured NOTHING for the burst prefix mints no head, reads `pending=0`, and PASSes the check whose entire purpose is that loss. go's own defect leaves earlier captures — and therefore a head — behind, so the go mutation armed the arm that already worked; the total-loss arm was never exercised by the go teeth. py proved it by mutating a py peer to stop capture outright: still 16/16 PASS. **The general law: reverting the fix on the authoring seat verifies the check against the authoring seat's failure MODE, not against the failure the check names on other seats — a portable oracle can be blind on a peer whose defect reaches a different arm of the same field.** Enforcement: when you author a cross-impl oracle check, enumerate the DISTINCT failure modes the named condition can hide (here: partial loss = head + uncaptured path, vs total loss = no head at all) and arm the check against each, not only the one the authoring seat exhibits; a spec-field oracle proves portability, and the mutation on your own seat proves only the arm your own bug reaches. Fix: convergence now requires `pending==0 AND head present` (`cmd/internal/validate/auto_version_burst.go`), closing the blind arm WITHOUT touching `status.pending`'s no-head semantics — that case is unruled (py SA-PY-28) and changing it would unilaterally converge go onto py's reading of the absent case, which the divergence rule forbids. **No new discipline for the fix itself** (it re-applies the fail-closed-control rule and the divergence rule); the earned line is the portability≠armedness law above. Owed onward: SA-PY-28 (arch rules the no-head arm; if go adopts py's reading the check is armed on all three seats with no further change), and rust's `guarded_publish` last-advance drop, which rust filed as found-not-fixed (same shape as our `ext/publishedroot`).
  > **Second bite, 2026-09-04 — the COVERAGE axis of the same law: a cross-impl oracle authored for a rule that spans N operations, scoped to the ops the AUTHORING seat's own measurement flagged, is blind exactly on the ops where the divergence is live on OTHER seats — and go-on-go cannot see the gap because go is conformant on all of them (rust + py both caught it).** The type-op 404 gate (`cmd/internal/validate/typeext.go`) probed only `converge`/`adopt`/`reconcile` — the three §12.2/§12.3 MAY ops go's own §3.3 measurement had named — and skipped `compare`/`compatible`, the §7.2/§7.3 SHOULD ops all three seats build and the row where PROPOSAL §6a.3's `not_found`→`type_not_found` narrowing is ACTUALLY live. So rust's and py's row-4 fix was cross-impl-invisible: rust's own `type` score was byte-identical before and after their fix, which is why rust asked go to EXTEND the gate rather than report it verified. Same law as the arm-blindness above, one axis over: there it was the *arms of one field*, here the *operations one rule spans*. **Enforcement: read the op-scope of the rule from the SPEC/PROPOSAL text itself (§6a.3 governs row-4 AND the MAY ops), enumerate every operation it names, and probe each — not only the ops your own seat's incident surfaced; the tell you under-scoped is that YOUR seat passes every probe while a sibling's live divergence sits on an op you did not add.** Companion defect the same review (rust caught): the check `SkipCheck`'d a conformant not-implemented `501`, and a SKIP counts as a failure — so a rust peer that builds 3 of 6 ops exited the suite 1 with zero failing rows, while the roundtrip row above WARNs the identical `501`. **A check that degrades to "not testable" on a CONFORMANT peer posture WARNs; SKIP is for "setup could not run" — and it matches the verdict of the sibling check probing the same op.** Both are re-applications (the every-surface/census rule on the op axis; "a skip counts as a failure," ADR-0012) — **no new discipline minted**, per the close-out floor; recorded because the coverage-scope shape is the second bite and the enforcement point (probe every op the rule's text spans; WARN a conformant not-implemented) is concrete. ## Proving a producer-side artifact is consumable: drive the consumer's real dereference

- **A self-authored proof of a deliverable a DIFFERENT impl consumes must exercise the CONSUMER's actual dereference, not a producer-convenient path that shares the producer's blind spot (earned 2026-08-20, browser-rust caught it — the C-7 B4 false-green).** I stood up go's federation publisher leg and "proved it end-to-end" by driving go's OWN consumer at it cross-container — and reported it done. The publisher signed a `root_hash` it did not serve (a hardcoded literal, not the served trie root); browser-rust's consumer fetches the signed root **by its content hash** as its first step and 404'd immediately, while my go proof passed because it verified the signature *value* over the hash and walked leaves by *path* — it **never dereferenced the signed root by its hash**, the exact operation whose failure IS the defect. This is "Go-on-Go passes deceptively, the cross-impl FAIL is the true signal" on a new axis: not a shared writer/reader helper, but a **shared verification harness that inherits the producer's leniency**. A go consumer built beside a go publisher tests what go emits, not what the contract requires; the one dereference that distinguishes a served root from a signed-but-absent one is the one a producer-convenient walk skips. **Enforcement: a proof that a producer-side artifact is CONSUMABLE must (1) perform the consumer's real entry dereference — for a published root, `GET /content/{hex(rootHash.Bytes())}` must resolve — and (2) carry a negative control (a wrong/old hash must 404), so the check is shown to discriminate; and a go-on-go pass is NEVER the gate for a cross-impl deliverable — the cross-impl drive is.** Teeth: `scripts/federation-publish.sh probe` fetches the signed root by hash with the old fake hash as the negative control; `cmd/publish-fixture` now publishes `tree.BuildTrieForPrefix(...)` (the real served root), not a literal.
  > **Sharpened 2026-08-20 (B4 half-2, browser-rust caught it AGAIN — the same rule one hop deeper).** Half-1's enforcement — "`GET /content/{hex(rootHash.Bytes())}` must resolve" — was satisfied while the served root was the canonical EMPTY node: `cmd/publish-fixture` wrote entries through `nli` (NamespacedIndex, keys `/{peer}/system/...`) but built the trie through the raw `li`, so `li.List("system/")` matched nothing → `BuildTrie(cs, nil)` → empty root, no error. The signed root verified AND served by hash (half-1 green), and still resolved zero keys. It stayed invisible to go-self because `cmd/fetch-published-fixture` resolves leaves via `FetchTreeLeafPointer` — a **path-index** lookup served straight from `li`, which never walks the signed root trie — so go's own consumer's terminal operation was never the root walk. Two enforcement gaps this exposes: **(1) the consumer-dereference the proof must perform is resolving a KEY THROUGH the signed root, not merely fetching the root by hash** — a root that serves-by-hash but resolves zero keys passes "the root resolves" and fails the contract; the dereference under test is the trie walk to a leaf (`tree.CollectAllBindings(cs, root, "")` in-process, `GET`-walk CHAMP-by-hash on the wire), with a negative control that a wrong/empty root resolves 0 keys. **(2) A writer and reader of one served structure MUST share one key space** — `nli` (writer) vs `li` (reader) disagreed silently and `BuildTrieForPrefix`'s list-with-relative-prefix / trim-with-qualified-prefix shape returns empty rather than erroring exactly when they disagree, so `git grep` the publisher for a `.List(`/`BuildTrieForPrefix` whose index arg differs from the index the entries were `.Set` through. Teeth: `cmd/publish-fixture/main_test.go` `TestPublishedRootResolvesEveryKey` (RED with `li`, GREEN with `nli`) + `TestPublishedRootWalkDiscriminates` (bogus + empty root → 0 keys). **No new discipline earned** — this is the half-1 rule with its dereference-target corrected from "root fetches" to "a key resolves through the root," recorded per the close-out floor; the go-self walk is a REGRESSION guard, the cross-impl drive is still the gate.

## A harness must transmit a resource limit through the channel the peer reads it from

- **A conformance harness must transmit a resource LIMIT through the SAME spec channel the peer READS it from — a limit sent on the wrong channel does not error, it silently DEFAULTS, so the tell is a boundary that equals the peer default, never a failure (earned 2026-08-22, the compute cross-bless did not lock — same deceptive-green family as "Go-on-Go passes, the cross-impl FAIL is the signal," on the axis of a shared DEFAULT).** The 362-vector compute cross-bless read `361/362` for a week: `cv9a-map-depth-exceeded-contains` (and `recurse/tail-sum`) forked because the wire driver (`cmd/internal/compute-corpus/peeremit.go`) sent only `params.budget` (operations) and EXTENSION-COMPUTE §5.2 sources the DEPTH limit *only* from the capability's grant-level `constraints["system/compute"]["max_compute_depth"]` (ENTITY-CORE-PROTOCOL §5), never from a param. So every depth-sensitive vector ran at the peer default depth (1024) and returned the full array where the in-process eval returned `depth_exceeded`. It was invisible go-on-go (both sides defaulted → agreed) and surfaced only cross-impl. **It compounded with a real go HANDLER bug on the same read:** `initBudget`/`reactiveBudget`/`EvaluateAtPath` read `constraints` off the capability TOKEN's top level (`cap.Data["constraints"]`), but per §5 `constraints` is a GRANT-level field (`grants[].constraints`; the token has no top-level `constraints`), so a compute depth/ops constraint had reached the evaluator *nowhere* since v0.8.0 — the field `HandlerContext.MatchingGrant` ("grant entry that passed CheckPermission (for constraints)") existed for exactly this and was unused. Two enforcement points: **(1)** for any resource limit a harness reproduces on a peer, confirm the *channel* — grep the handler's `init*Budget`/limit-read for what field it consults, and drive the limit through THAT (here: mint a cap whose matching grant carries the constraint via `SendExecuteWithCap`, not a param); the acceptance proof is a route-A-vs-route-B LOCK (go-in-process vs go-over-wire, `cross-bless` 362/362), which is what a silent default cannot pass once the vector is depth-sensitive. **(2)** a handler reading a §5 grant-level field (`constraints`, and its siblings) off the token top level returns nothing for every conformant capability — `git grep` reads of `constraints` in a handler and confirm they resolve the MATCHING GRANT (or scan the token's grant entries), never `token.Data["constraints"]`. Teeth: `ext/compute/depth_constraint_test.go` (grant-level `max_compute_depth` lowers the budget through `initBudget`; mutation = strip the constraint, default stands) + the go-on-go wire LOCK; the §5.2 pseudocode that misled the read (`capability.data.constraints`) is routed as spec-issue `2026-08-22-a` so rust/py don't inherit the same silence — the cross-impl re-drive of the 362 corpus is the confirmation that owes.

## A wire check must not discriminate on an unruled / cross-impl-divergent semantic

- **A wire conformance check MUST NOT discriminate on a value that depends on an UNRULED / cross-impl-divergent spec semantic — such a check tests the contested reading, not the feature; it passes only against the impl that shares its reading; and its green is a false signal that ONLY a cross-impl run exposes (ratified 2026-08-18/19, rust caught it — a second bite of "Go-on-Go passes deceptively, the cross-impl FAIL is the true signal," on a new axis).** `registry.v15_dispatch_grammar` (08684b2) tried to observe the §4.1a *matcher grammar* by watching `resolved` vs `chain_exhausted` — but "does an UNMATCHED name still resolve?" **is** the §4.1 step 2 *filter* question, which is unruled and go/rust read opposite (go: unmatched → unfiltered → resolved; rust: unmatched → scoped away → chain_exhausted). So the check measured the filter, encoded go's reading, passed go-on-go, and FAILed a conformant rust peer — a false conformance signal (ADR-0012). Worse, the negative-match row (the only one that distinguishes our grammar from `path.Match`) IS inherently the contested filter case, so **no honest wire check exists here until §4.1 is ruled** — the grammar's teeth belong in-tree (`glob_dispatch_test.go`), where they are uncontested. The published-root path fix this same session was the *sibling* bite (shared writer/reader helper → Go-on-Go green → Rust consumer caught the EISDIR), so this pattern bit **twice this session** and is ratified. **Enforcement: before landing a wire check, name the exact observable its PASS/FAIL turns on, and confirm every conformant impl agrees on that observable under the SETTLED spec; if the discriminator rides an open spec-issue (or a `git grep ../entity-core-*` shows a sibling reading it differently), pin the feature in-tree and DEFER the wire check with a comment naming the spec-issue.** A green wire check that can only be green on the impl that wrote it is not evidence — it is the deceptive-green trap wearing a conformance badge. (Removed; §4.1 step 2 routed as spec-issue `2026-08-19-a`, concurring with rust.)
  > **Forward half, 2026-08-19 (a) — a check deferred for an UNRULED discriminator is a REVISIT obligation on the ruling, not a permanent grave; and the same check text flips from deceptive-green to true-signal the moment the semantic settles AND every conformant sibling is verified to agree.** §4.1 step 2 was ruled at [1.14] (`86643f8`) — the filter discriminator is now settled — so the deferral reason changed from *semantic* (unruled) to *sequencing* (arch's §4 ruling that round: constructible only once rust + py also land row 2, else it FAILs a not-yet-landed conformant peer). The v15 filter vector therefore STAYS pulled, now for the sequencing reason, and the revisit is recorded in the check's own comment (`cmd/internal/validate/registry.go`). **The sibling grammar check went the other way and proves the rule's teeth:** `name_constraints`'s grammar was *also* unruled and its wire vector was withheld — but 1.15 SETTLED it, so `name_constraints_grammar` became constructible, and a cross-impl run (not go-on-go) confirmed it: **go + py PASS, rust FAIL** on a settled semantic. A FAIL against a settled-and-cross-impl-verified discriminator is a TRUE conformance signal (rust owes the landing); a FAIL against an unsettled one is the deceptive trap. The enforcement gains one clause: **when the spec-issue a deferred check named is CLOSED, re-evaluate the check — (a) is the discriminator now settled? (b) does a cross-impl run show every conformant impl agreeing? Only then land it; a green-on-author-only recheck means it is still riding contested ground.** No new discipline (the forward reading of the same rule); recorded because the revisit is the step a "deferred pending ruling" note otherwise silently drops.
  > **DISCHARGED 2026-08-19 (b): the filter vector's revisit fired and it landed as `v4b_meta_resolver_filter_fail_closed`.** The two-clause test above was run, not asserted: (a) the §4.1 step 2 discriminator is settled ([1.14], `86643f8`); (b) a cross-impl run — not go-on-go — shows every conformant impl agreeing: **go + rust + py each PASS registry 15/15**, the vector green on three independent codebases (peers built fresh at rust `898e55b`, py `1cb7c01`, the row-2 landings the sequencing gate named).
