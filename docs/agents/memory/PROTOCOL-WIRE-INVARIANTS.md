# Protocol Wire Invariants

Wire-format and dispatch invariants whose violation is a silent hash mismatch or a blind gate, not a failing test. Read before touching the receive boundary, ECF, paths, or the dispatch context.

## Raw-message preservation blinds gates to a non-canonical construct inside the data (DR-3), and any byte-identity decision

  > **The SAME raw-message preservation that protects byte fidelity BLINDS every downstream gate to a non-canonical construct INSIDE the data — a receive-boundary canonicality rule (no CBOR tags, §6.3) must be a SEPARATE explicit walk over the data bytes, because hash validation and the typed decode both structurally cannot see it (candidate, first bite 2026-09-16 — the DR-3 gap; rust AND py each found it in their own trees and flagged go).** 0.8.2.26 DR-3 withdrew §4.11's framing-arm ban on `non_canonical_ecf` and PARTITIONED the input: a tagged-but-decodable frame moves to `ENTITY-CBOR-ENCODING` §6.3 (older than the fold, never implemented on any go boundary). go's relay scored the whole `.26` fold *"nothing in either of your trees moves"* — true for eight deltas, FALSE for DR-3, and false in the direction a delta-counting reader cannot see (§0's *"no delta adds an obligation to a conformant peer"* is true and does not reach a rule the withdrawal handed the input to). **DRIVEN, not reasoned (both siblings marked go `[code read, NOT a drive]`; the drive is the signal):** an EXECUTE whose entity `data` carried a CBOR tag was ADMITTED 200, identical to its untagged twin — a peer rust and py refuse, served. Why every gate was blind: the receive decoder runs default `DecOptions` (tags allowed), `Entity.Data` is `cbor.RawMessage` (captured raw), so a tag in a data field is never parsed by the entity decode AND a tagged entity self-verifies (the sender hashed the same tagged bytes) — hash validation cannot see a construct it hashed over. go's only strict-ECF validator (`cmd/.../strict.go`, `TagsForbidden`) had NO caller on the protocol boundary — the third *"validator with no consumer"* in this class (rust ratified it), the sibling of *"a Skip-on-missing-file guard is only a guard if its path is live."* **Three enforcement points. (1)** a ruling that WITHDRAWS a prohibition is not a no-op — grep the spec for the rule the withdrawn input is handed to (`ENTITY-CBOR-ENCODING §6.3`) and ask *do I implement THAT*, not *does this delta oblige me*; a relay's per-delta *"does your tree move?"* **"no"** on a withdrawn-prohibition row is exactly where the real work hides, and relaying arch's scoring faithfully does not make the "no" true of your tree. **(2)** a receive-boundary canonicality rule binds at the ONE boundary primitive every transport shares (`Envelope.ValidateAll` — TCP `validateRecv`, http-connection, httplive, `wire.ReadEnvelope`, the `protocol` dispatch pre-validator all pass through it), as an explicit walk (`ecf.ForbidTags`, any-depth major-6 reject) — NOT in the typed decode (blind to a raw-message field) and NOT as an uncalled `cmd/` validator. **(3)** a NEW receive-boundary refusal that rejects a WHOLE-decoded frame MUST keep the connection (§4.9(c): the stream is synchronized on the next boundary, so serve() CONTINUES on the coded 400, matching the pre-admission undecodable arm, the dialer reader, and rust/py) — a close cascades on a shared multiplexed connection, and **a green go-on-go unit suite cannot see it; the release gate is what surfaces it.** The cascade here was concrete and instructive: the CAP-6a ingest check mints an out-of-range temporal field, which go's ECF encoder serialises as a **bignum tag 2**, so DR-3's boundary check now refuses it as `non_canonical_ecf` (both refusals fail-closed — the CAP-6a security property holds either way), and the pre-fix close destroyed the shared connection → **961** later checks cascaded to FAIL, invisible to `go test` (68 pkgs green) and caught only by `validate-complete.sh`. Wide reading (§6.3 any depth, incl. tag 55799 — item A/SA-PY-66 answered by drive: go is wide, matching rust/py, so row (5a)'s narrow *"data-field position"* describes no impl). Teeth: `core/ecf.TestForbidTags`, `core/peer.TestDR3_TagInDataFieldRefused` (wire, incl. 55799), `core/peer.TestDR3_TagRefusalKeepsConnection` (§4.9(c)), all mutation-verified both directions. Owed onward: routed to arch (fold row (5a) to §6.3-wide; the whole-decoded hash/key-binding failure's own close-vs-continue question) and cohort (the 3-way tag drive). Same *"cross-impl signal is the true signal"* + *"run the gate to a true exit 0, not go test"* family, on the axis of a withdrawn prohibition + a raw-message-blinded boundary.
  > **RATIFIED 2026-09-16 — a spec sentence that PINS one property (a code) does not license inferring a SECOND property (an ordering, a disposition) from its neighbourhood; when your IMPLEMENTATION's behaviour on an unstated property is DERIVED FROM a code-pin's wording, that derivation is a spec-issue to route, not intent to implement — and the tell is that a code COMMENT reasons its way to the inferred property. Two bites one arc apart, DIFFERENT shapes (ordering vs disposition), neither found by review — promoted (this is arch's `0.8.2.29`-B / `0.8.2.30` pattern, adopted; it bit GO directly both times).** DR-3's "Owed onward … close-vs-continue" question above is now RULED and LANDED as the second bite. **Bite 1 — item B (`0.8.2.29`, arch's round-4 relay §4): CONTINUE.** go's `serve()` had THREE dispositions on a whole-decoded `validateRecv` failure (close on hash/key-binding, continue on tag) — the close was inferred from N4's CODE pin (`hash_mismatch`), which pinned no disposition. Every failure at that point is whole-decoded (RecvEnvelope already decoded the frame → stream synchronized on the next boundary), so §4.9(c)/§4.10 make CONTINUE the only disposition conformant on a multiplexed connection; the per-cause split was the smell. Fixed `core/peer/connection.go` (the arm `continue`s unconditionally; the only forced close is a DESYNCHRONIZED stream — truncated/oversize — handled in `classifyRecvError`). Teeth: `TestServe_HashBindingRefusalEmitsCodedFrameAndContinues` sends a SECOND mis-keyed frame and requires its own coded 400 — mutation-verified RED (restore the `return` → the second read EOFs). **Bite 2 — CQ-30 (`0.8.2.30`, arch's ruling §1): 501 is POST-`check_permission`; go was the live outlier and it was a SECURITY leak.** go's `execute.go` ran `checkOpInManifest` (→501) BEFORE the capability check, and the code comment reasoned the ordering from §6.2's *"the caller's authority is irrelevant"* — which is a CODE rule (do not report an authorized caller's undefined op as 403), never an ORDERING rule. §6.7 refutes the operation-enumeration oracle **on the strength of this order alone**: op-existence-first makes 501-vs-403 a two-valued oracle over a handler's manifest for any caller holding *any* grant on the path. go's bootstrap grant covers `system/tree`×`get`, so anyone holding it could enumerate `system/tree`'s operation set. Fixed by moving the 501 check BELOW `FindMatchingGrant` (Dimension 1 gates on the operation, so an unauthorized+undefined op is 403; an AUTHORIZED caller — wildcard ops — still gets 501, leaking nothing). go ACCEPTED the ruling without argument (spec MUST, confirmed live, divergence rule). **Enforcement, two points, both concrete: (1)** grep any spec/routing sentence that PINS a code and ask what UNSTATED property (order, disposition, retry) your code infers from it — if a comment or a test NAME reasons to that property, it is derived, and a derived property is routed, not shipped. **(2) an authorization-ORDERING leak is invisible to every gate whose client drives the code row under a WILDCARD/covering cap** — the validate connection cap is `OpenAccessGrants` (wildcard ops), so the 501-row check measured the row and never the order; the ordering surfaces ONLY under a cap UNAUTHORIZED for the probed op. Pair any code-row check with a scoped-cap probe that lacks the operation grant and assert 403 (`cmd/internal/validate/connectivity_section33.go` `undefined_op_unauthorized_is_403_not_501`, mutation-verified ON THE WIRE — reintroduce op-existence-first, rebuild the peer, the probe flips 403→501). Both bites: gate a true `PASS 0..5 exit 0` @ `<this commit>`, `-race` clean, register unchanged. Owed onward: the cohort DRIVES CQ-30 (arch relay §5 item 1 — rust/py have the same order to verify, and no existing check drives it); the `ECP-R44` re-score is arch's (its prior PASS is void under CQ-30, handed to the conformance seat, not go's file).
  > **Broadened 2026-08-20 (rust caught it): the no-decode-then-re-encode rule governs ANY byte-identity DECISION, not just entity-data hashing — and a spec's word `byte-identical` is the tell.** The §4.3 pin-delta compares the submitted `pinned_bindings` against the stored ones; my first cut re-encoded the *decoded* `[]PinnedEntry`, which drops a §4.2 forward-compat key a pin may carry — so a config that adds or strips that key read as "no change" and rewrote the registry's **most privileged row** (a pin bypasses the §4.1 step-2 filter and the §6a.9.1 ceiling) under `registry-configure` alone. **Fail-open, on the exact row the check exists to protect.** Same root cause as the entity-data rule, one field deeper: a decode-then-re-encode is lossy on unmodelled keys, and a byte-identity comparison is exactly where that loss becomes a security verdict rather than a hash mismatch. Enforcement: when a spec MUST turns on `byte-identical` (or you are comparing two encodings of the "same" value for an authz/dedup/change decision), compare the **raw field bytes** (`cbor.RawMessage` extracted from the stored entity's `Data`), never a `Decode → re-Encode` of the typed struct. `git grep` for `ecf.Encode(` on a decoded value feeding a comparison. Teeth: `ext/registry` `TestPinDeltaComparesRawBytesNotDecoded` (mutation-verified). The Go-on-Go unit suite could not have witnessed this — go's own codec never emits the unmodelled key, so only a hand-built forward-compat fixture (or a cross-impl peer) bites; **rust reading `byte-identical` literally is what found it**, the same "cross-impl FAIL is the true signal" shape as the invariant-pointer path.

## Wire-entry and in-process dispatch populate the handler context by different mechanisms

- **The wire-entry and in-process-entry dispatch paths populate the handler CONTEXT by different mechanisms, so an equivalence test that asserts only the RESULT misses a field one path drops (earned 2026-08-18, workbench-go caught it with a kernel reproducer).** `handleExecute` (wire) seeds `hctx.Resource = normalizeResourceTargets(...)` **directly** on the handler's context; `DispatchLocalExecute` (the SDK entry, how every in-process consumer dispatches) instead re-dispatches through `makeLocalExecute`, whose child context takes its resource from `execOpts.Resource` — **not** from `rootCtx.Resource`, because that closure is also the sub-dispatch path where §5.2 forbids inheriting the parent's resource. So `DispatchLocalExecute` set `rootCtx.Resource` and it never reached the handler: every in-process ENTRY dispatch that named a resource dropped it to nil, silently, at 200. `dispatch_equivalence_test.go` asserted RESULT-hash equality across the two surfaces and `subdispatch_resource_dimension_test.go` drove both sub-dispatch directions — but nothing entered through `DispatchLocalExecute` with a resource and read it back off the handler's context, so the drop was invisible for as long as it existed. The rule: **when two entry paths claim observable equivalence, the equivalence test asserts the handler-visible CONTEXT (resource, bounds, caller-cap, every dimension the two paths set by different mechanisms), not just the Result** — a field the wire path sets on `hctx` directly and the local path must thread through an `ExecuteOption` is exactly where a newly-added field silently diverges. Enforcement: `TestDispatchLocalExecute_CarriesResourceToHandler` (a handler that records `req.Context.Resource`, driven through the entry point, teeth-verified red pre-fix); when you add a field that the handler context carries, assert it reaches the handler through BOTH entry surfaces. (Fix: `DispatchLocalExecute` passes `handler.WithResource(req.Resource)`, mirroring wire entry.)

## A restart-durable rollback-defense counter held only in memory silently rolls back

- **A restart-durable rollback-defense counter held ONLY in process memory silently rolls back on restart — recover it from the store at startup (candidate, first bite 2026-08-18 (r), workbench-go's cross-impl run).** `ext/publishedroot`'s publisher minted `seq` from an in-memory `lastSeq` that started at 0 every construction, so a process restart republished `seq=1` over a store that already carried `seq=N` — and §6.5.3.1 makes `seq` a **rollback defense**, so every consumer that saw `N` rejects the new head, the defense working as designed against a bug. The tell it was a bug and not a design: **the same concept was already implemented correctly one directory over** — `ResolutionLogData`'s §11.2 seq "is recovered on startup by walking this prefix and taking max+1" (`core/types/registry_ext.go`), and published-root simply didn't do the equivalent. Same meta-shape as the (g) family: one place got a concept right, another held it in memory only, and **nothing compared them**. The rule: **a monotonic / rollback-defense value that is bound in the durable store MUST be recovered from that store before the next mint, not carried in zeroed process memory** — held in memory it is correct until the first restart and then silently wrong, which no same-process test can see. Enforcement: `TestSetupAuthorityRecoversSeqAcrossRestart` drives two publishers over ONE store+index and asserts the second continues the chain (teeth: seq=1 without the recovery); when you add a store-bound counter, add a two-lifetime restart test, and `git grep` for a sibling that already recovers-on-startup before writing a fresh one. (Fix: `SetupAuthority` reads the bound head at `PublishedRootStoragePath()`, seeds `lastSeq`=`pr.Seq` and `lastHash`=the bound hash.)
