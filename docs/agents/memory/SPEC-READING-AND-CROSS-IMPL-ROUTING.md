Reading the spec, making claims about sibling implementations, and routing findings. The recurring failure is a plausible sentence about another repo (or the spec) that nobody opened the tree to check.

## Converging an error code — the conformance unit is the status slot, not the token an incident named

- **Converging an error CODE, the conformance unit is the status SLOT — the SET of spellings emitted at that status — never the single token an incident named (candidate, first bite 2026-09-03, arch's 0.8.2.7 slot ruling caught it).** `0a6d3c9` swept `400 unknown_operation → 501 unsupported_operation` and closed out the 501 row as done; five other 501 spellings the incident did not name survived — `not_implemented` ×6 in go (`execute.go:293,667`, `local.go:454`, `compute/handler.go:137,144`, `peerissued/register.go:391`), plus `not_supported`/`unsupported_mode`/`not_available` cohort-wide — so the slot stayed divergent while the sweep reported complete. A token-scoped sweep is done-looking and wrong: a client branches on the code, and two spellings at one status IS the divergence whether or not the incident named both. The identical shortcut produced the spec's false "three implementations converged on `internal_error`" (0.8.2.6) — it measured one spelling instead of censusing the slot, and "N converged on X" is a positive-sounding claim whose truth condition is a negative, so the prove-a-negative rule never fired (arch's AP-21/L8). Enforcement: when you converge an error code, census the whole slot FIRST — `grep -rhn '<status>, "' core/ ext/ | grep -oE '<status>, "[a-z_]+"' | sort | uniq -c` — and converge every generic-case spelling to the spec-named default (leaving only codes DEFINED in a spec code set); a sweep close-out quotes the slot census, not the one string it changed. Same family as "enumerate every surface a rule names," one axis over: there the surfaces a rule touches, here the spellings that occupy one status slot.
  > **The layer BELOW the slot — the code must live in the `code` FIELD, not merely be a field carrying the right spelling (candidate, first bite 2026-09-03, a go harness fix caught core-rust).** The slot census above counts `(status, spelling)`. It is blind to a code carried under the WRONG KEY: core-rust's type-system handler answered `501` with `{type: "unsupported_operation", message: …}` — right status, right spelling, wrong field — from a local `error_entity` (`extensions/type-system/src/{validate,constraint}.rs`) that shadowed the canonical `core/handler` one (key `code`). A conformant client reading `result.data.code` (§3.3 `system/protocol/error := {code, message}`) gets `""`; a `grep` of the raw error map finds the string under `type`; go-on-go never sees it (go emits `code`). This survived 0.8.2.5→0.8.2.7 and two cross-impl sweep rounds because no unit anyone counted could see it — the same "census keyed on the wrong axis" root as the registry drip-feed, and the same "shadowing local helper diverged from canonical, nothing compared them" meta-shape as `globMatch`/`matchPattern`. Enforcement: the conformance unit is `(status, code-read-from-the-`code`-key)`; a §3.3 error-code check reads the code via the `code` field ONLY and FAILs a code found under any other key — never a raw-map fallback that reads any key, which launders the defect (`decodeResultErrorCode` reads `code` only, by design; `classifyOptionalTypeOp` FAILs the empty-code case rather than reading `type`). Method (A1, trace the value a real client reads): the tell was `result.data.code=""` under `decodeErr=nil, resultLen=156` — a successful decode with an empty read points at the field key, not a decode bug. Teeth: `cmd/internal/validate.TestClassifyOptionalTypeOp` (`not_impl_501_empty_code_fails`, mutation-verified — dropping the code guard reds it). **A code is `(status, field, spelling)` — three axes, and a census that fixes two is blind to the third** (core-rust promoted the same triple in their charter). **The enforcement point must name the MINT-SITE region, not the call site: an impl-local `error_entity`/error-mint helper that shadows the canonical one is invisible to a call-site grep** — which is exactly how this survived three spec revisions and two cross-impl sweeps (core-rust confirmed: `4d888f8` had just landed `unsupported_operation` at those very sites, so the slot was right, the spelling was right, the field was wrong, and every census counted the 501 row closed). Enumerate every mint site of the substrate error entity and extract the field key at each — core-rust did this and found exactly 2 defective of 25, both the shadowing helper's; a grep of the constructor (`error_entity(`, `cbor_map!`, the `{code:` literal) across the whole crate, not the dispatch call sites, is what surfaces a divergent local mint.
  > **The ROUTING axis of the same law, and it bit us both directions at once (candidate, 2026-09-05, core-rust caught it): when you ROUTE a sibling's error-CODE defect, the evidence is the OBSERVED `result.data.code` from a DRIVE — never a `git grep` of the code TOKEN, because the token can sit in the human MESSAGE while the dispatcher/wrapper supplies a different, possibly-DEFINED code.** Cycle 4 routed rust two tree:put lines as an `invalid_entity` defect, grepped from their source. Both were `HandlerError::InvalidParams(format!("invalid_entity: {e}"))` — the token was in the *message*; the dispatcher emitted `invalid_params` (a DEFINED §3.3 specific). So the ledger was wrong twice over: rust never shipped `invalid_entity` (closing the item as titled would assert a defect they did not have), and the real defect was *worse* than the one named — `invalid_params` passes any grep for undefined tokens while still costing the caller the branch the two-row split exists to give. The one real `invalid_entity` EMISSION was in `content:ingest`, a handler the token-grep of tree code never looked at. Two enforcement points. **(1)** A routed sibling error-code claim cites a driven `(status, code)` pair or is marked "unverified — drive before acting"; a claim whose evidence is `git grep <token>` is not evidence of the emitted code, and the unverified code MUST NOT go into the ledger/table AS the defect (hedging in prose, as cycle 4 did, is not enough — the table still asserted it). **(2)** A source read of a sibling's error codes is blind to an UNCAUGHT-exception path: driving the new `put_undecodable` wire check surfaced py answering `500 internal_error` for a non-decoding put entity (a client-triggerable 500 where EXTENSION-TREE Appendix A v4.4 row 1 mandates `400 invalid_request`) — a 500 that NO error-code string in py's source produces, so no grep could have found it; go and rust both return `400 invalid_request`, so the cross-impl FAIL is the true signal. Same triple `(status, field, spelling)` as the block above, now on the routing axis: read the code a real client reads (drive it), not the token a grep finds. This is why the tree:put row is verified by a wire check driven three ways, not by three source reads. Re-application of "the conformance unit is the code read from the `code` key" + "the cross-impl FAIL is the true signal"; recorded because it bit on the routing axis and cost a doubly-wrong ledger, corrected in report `docs/validation/reports/2026-09-05-b-*`.

## 'Filed, not yours' is about provenance, not ownership

**"Filed, not yours" is about provenance, not ownership — a normative change to a definition site we
bind against is owed work no matter which section announces it (earned 2026-08-18 (m), arch caught it).**
We acknowledged arch's `-i` ask to confirm "any doublestar dependency removed" and it was **false**:
go carried the §4.6 `type_pattern` doublestar matcher (`ext/type/constraint/globMatch`) the whole time,
and we confirmed "removed" without opening it — because `-i` filed the §4.6 fold under a heading
("Arch-owed, filed, not yours") that told three engine seats the change was not theirs. It was *their
defect to fix* (provenance) but a definition site *we implement a matcher against* (ownership of the
follow-on), and all three of us confirmed removal of a dependency we all still had. Our own spec-issue
then reasoned from the pre-fold §4.6 text, two commits stale. **The rule: when a fold/ruling touches
spec text this repo implements a matcher / encoder / validator / canonicalizer against, open THAT
surface and re-read our code before acknowledging anything about it — regardless of whether the packet
files it as ours.** Enforcement: an acknowledgement of "removed / changed / conformant on X" names the
`(file, symbol)` it checked (here `ext/type/constraint/handler.go` `globMatch`), never a bare "confirmed";
a §-heading that says "not yours" is not evidence about our tree, only about whose defect it was. Same
family as the sibling-negative miss — the sentence nobody opens the tree for is the one that ships wrong.
  > **Second bite 2026-09-16 (recorded per the close-out floor — re-application, not a new discipline): a relay-packet section headed "for relay to rust and py" whose rows are tagged "all three, and this is behaviour" contains GO obligations, and the tell you almost missed one is answering "are we good?" without opening the tree.** arch's round-4 relay §4 relayed 0.8.2.29's round-4 items as rust/py's worklist; five rows were marked "all three." Tracing each against go's own tree (not the heading) found go conformant on 4 (system/peer two-field shape, the §1.5 correlation MUST-NOT by absence, the §4.5a floor) and **non-conformant on one — the §3.6 rule-4 `peers.exclude` fail-open** (`matchesIDScope` is a bare literal matcher; a non-canonical-form exclude silently does not match → the named peer is not excluded). go-on-go with the Ed25519 default (canonical `0x00` identity-form) never exhibits it; it surfaces cross-impl / non-default-key / crafted-cap — the standing "go-on-go passes, the cross-impl/crafted case is the signal" shape, on the authz guard. It is landed spec and unambiguous, so it was owed GO work (not a spec-issue) and is now FIXED: `crypto.CanonicalizePeerID` (form-only §1.5 canonicalization — recover from an identity-form value, ok=false for a SHA-256-form/malformed/unknown-key one that cannot be canonicalized without the pubkey) + a SEPARATE `core/capability.matchesPeerScope`/`peerPatternMatches` (kept off the shared `matchesIDScope` so the operations dimension never gets peer-id canonicalization), applying the §3.6 rule-4 fail-closed dispositions — an unresolvable include is withheld, an unresolvable exclude MATCHES (excludes). The exact-literal and `*` fast paths preserve prior behaviour byte-for-byte, so only a non-canonical entry changes. Teeth: `core/capability.TestPeersScope_Rule4_NonCanonicalExcludeFailsClosed` — a SHA-256-form exclude naming the target MUST exclude it, mutation-verified RED against the literal matcher, with a positive control (a canonical exclude of a DIFFERENT peer must NOT over-deny) distinguishing "fail closed on unresolvable" from "exclude everything." Enforcement: when a relay/round packet marks a row "all three" or "this is behaviour," trace it against go's own `(file, symbol)` before reporting go clear — the heading names whose worklist it is for, never whether go's tree already satisfies it. (Same cycle, the CQ-30 3-way drive MEASURED the inverse cleanly: rust + py already answer `403` — the portable check PASSed against both — so go was the sole CQ-30 outlier and rust/py owe no fix; a measured cross-impl PASS is how "are we good?" gets answered, not a delta count.) The fix re-applies the 0.8.2.21 unmatchable-sentinel scope-position asymmetry (fail-closed in include, fail-open→now-closed in exclude) on the id-scope surface — no new discipline, recorded per the close-out floor.

## Verifying build-state and sibling claims — read the live worktree (the accumulated instances)

**It fails in both directions.** A capability note can be wrong by being **ahead** of reality as
easily as behind it — `--publish-root` once asserted republish-on-change as though the spec
required it, when no landed spec obliges a publisher to republish at all. "Rust + Python pending"
outlived the gap it described; "honored by all three" preceded the rule it implied. Both are the
same defect, and both read as a sibling bug that isn't there.

This applies hardest to **`cmd/peer-manager` flag help**, which is where these claims accumulate:
every `Honored by …` / `… impl pending` string is a build-state assertion about a repo we do not
control. Re-verify them whenever a sibling moves, and treat a stale one as a defect, not a typo —
it is the documentation of a skip.

**A fresh shape, 2026-08-15 — routing an obligation onto a surface a sibling doesn't serve.** When
routing `reflection_endpoints` (§4.5.1) to rust and py, the report instructed each to apply the
field on "both surfaces" because §2.2 binds the wrapped **and** the §9.2 unwrapped `advertise`.
**Both peers corrected it: neither serves the unwrapped surface** (rust prints `surface: wrapped`,
py has no `create_datagram_endpoint`), so §2.2's "both" collapses to the one wrapped surface in all
three — as it does here. I verified the *field* was absent but asserted the *surface existed*
without opening the tree — the "ahead of reality" defect in a new dress: a §2.2 obligation is only
routable onto a surface the target actually serves. **Before routing "MUST appear on both
surfaces," confirm the sibling serves the second surface** (`git grep` the listener, not just the
field). Same root cause as the flag-help staleness — a build-state claim asserted, not read.

**RATIFIED 2026-08-15 (f) — the sentence about the sibling is the one nobody verifies.** This has
now bitten **twice in two sessions**, both from a grep miss on a *sibling's* tree: the "both
surfaces" claim above, and a report that called py's §5.4.1 status **"unverified"** when py had
`test_keepalive_no_cadence_writes` passing all along — I searched `keepalive`+`write_status` and the
test's name did not match, so a present regression test read as an absence. Rust and py each
independently promoted this to a discipline in their own charters; it is earned here too (bit us
twice, different shapes → ratified, per the promotion ladder). **The rule: a claim about a sibling's
state — built / not-built / verified / unverified — gets the *same* open-the-tree standard as a
claim about our own, and a NEGATIVE about a sibling ("absent", "unverified", "built nowhere")
requires an exhaustive named search, including their TESTS, not a single grep of production code.**
A grep that finds nothing is not evidence of absence; it is evidence your pattern missed. The
enforcement point: before a report asserts a sibling lacks something, `git grep` the sibling for the
feature by **behavior and by test name**, not one keyword — the reports are right about their author
every time and wrong about the neighbor, because the neighbor sentence is the one that ships
unverified. (Corrected instances: `docs/validation/reports/2026-08-15-{b,e}-*.md`.)

**2026-08-16 — cite the commit that CONTAINS the work, not the commit that REPORTS it (arch's AP-12).**
We pinned py's v1.23 collector at `a6140a8` and stated it "built its collector." Arch, verifying rather
than accepting, found `a6140a8` is **docs-only** (an `AGENTS.md` + a status doc — and titled, aptly,
*"ratify the hearsay discipline — a report was wrong about us twice"*); the actual collector is
`5fbb8f3` (+233 / +370 tests). The conclusion was right, only the pin was wrong — but a pin is a
build-state claim, and a docs/status commit that *describes* a feature is not the feature. This is the
same family as the flag-help staleness and the sibling-negative miss: a sentence about a neighbor that
reads correct and wasn't opened. **The enforcement point: a commit pin asserting a sibling built X must
name a commit whose DIFF contains X (`git show --stat <pin>` shows the code, not just docs); a
docs/`AGENTS.md`/status-only commit is never the citation for an implementation.** Arch notes this class
has bitten four times and they've caught two — the peer verifying our pins is doing work we owe
ourselves.

**2026-08-19 — a subagent's claim about a sibling is STILL a build-state claim; pin it to the live
symbol at HEAD before routing it (earned — arch caught a three-way divergence I routed that had been
closed for a week).** The registry drip-feed packet claimed the §6a.9 layer-1 error strings diverged
three ways (`rust invalid_signature` / `py proof_failed` / `go signature_invalid`). I verified go's
own constant directly, but relayed rust's and py's from **sibling-inventory subagents that read a
COMMENT recording a *previous* value** and reported it as current — the strings had converged to
`signature_invalid` on 2026-08-12. The existing sibling-negative rule ("a claim about a neighbor gets
the same open-the-tree standard as a claim about us, and a negative needs an exhaustive named search
including tests") already covered *me* reading a sibling; the new clause is that it covers a
**delegated** read too. Enforcement: a subagent reporting "impl X answers Y / lacks Z" is reporting a
build-state claim, and "the subagent found the string in the tree" is NOT "the current constant is
that string" when the hit sits in a comment, a historical note, or a stale doc — **spot-verify a
cross-impl DIVERGENCE claim against the live symbol (`git grep` the constant at HEAD) before routing
it**, and when you delegate sibling recon, instruct the subagent to cite the defining symbol, not
prose. A divergence is the highest-stakes sibling claim there is (it routes a ruling), and it is the
one most worth one `git grep` before it ships.

**A `[MUST]` that needs a value but names no config site — and no vector — is unimplementable-consistently:
route it, do NOT invent the site (earned 2026-08-19, four bites in one shape — the registry drip-feed audit).**
core-py named the class exactly: *"a `[MUST when present]` with no declared site is a rule two conformant
peers cannot both implement."* The proof is measured, not argued: EXTENSION-REGISTRY §6a.9.1 makes the
resolver-side TTL ceiling `min(binding.ttl, local_max)` a `[MUST when present]` and the spec itself calls
it *"the load-bearing one"* — but declares no `local_max` field, so **go put it in a builder option

none interoperable, an operator's config artifact clamping on zero of them.** Same shape bit four times
(SA-PY-15, SA-PY-21 Q2 the MAY-override-with-no-field, R-OPEN-1 the register-request code strings, `2026-08-18-a`
the mint refusal code). This is the **spec-reading** sibling of the surface-enumeration family: those rules
guard *our own* impl surfaces; this one detects *under-specification in the spec we consume*, before code.
**Enforcement: on a new `[MUST]`/`[MUST when present]` that names a value, confirm the value has (a) a declared
config field and (b) a conformance vector; if either is absent, that is the spec-issue to route BEFORE
implementing — and inventing the site is the anti-pattern, because three invented sites is three homes no
operator can target.** The corollary the same audit earned: **a wildcard-MATCHING rule being unified (registry
v1.15, "the ONLY name matcher") does NOT unify character-LEGALITY** — §6.3 (no `/`) vs §11.1 vectors (`/`-names
matched) are separate regimes; "what `*` means" and "what bytes a name may contain" are two rules, and a
conformance vector that asserts one while violating the other is unconstructible on the wire (`2026-08-19-b`).
The audit + the consolidated cohort packet for arch: `docs/reviews/2026-08-19-registry-drip-feed-audit-and-consolidated-arch-packet.md`.
Its process finding is not a go discipline but belongs on the record: the drip-feed's root is **no single
reconciled open-items ledger** — "board closed" gets declared on one party's local view while items sit open
on another's (SA-PY-15 was dropped, R-OPEN-1 never entered arch's board), so gaps are rediscovered and routed
one tile at a time instead of ruled as a family.

## A 'routed divergence, not a defect' classification needs a conclusive control

**A survey classification of "routed divergence, NOT a defect" requires a CONCLUSIVE control — an inconclusive control is a reason to INVESTIGATE, not a licence to call the other seat's result conformant (candidate, first bite 2026-09-13, py caught it in go's own survey).** go's three-way survey filed py's `include_payload_overlapping_exclude` 403/403 as "already-routed Q2 divergence, not a defect" — every clause true, conclusion wrong. It was an ordinary py bug (a wrong handler argument), and **a question being open upstream (routed to arch) does not make the behaviour under it conformant.** The survey itself noted py failed the well-formed positive control (denied the non-overlapping subject too); a peer that fails the control cannot attribute its refusal to the thing under test. **Enforcement: before classifying a cross-impl result "conformant divergence, routed," confirm the peer PASSES the arm's positive control; if it fails the control, the classification is "likely defect — investigate," and routing the spec question is a SEPARATE act from blessing the behaviour.** The divergence rule governs whether *go* changes, never whether the *other seat's* result is a bug — conflating the two mislabels a defect as a spec question and stops the investigation that would have caught it.
