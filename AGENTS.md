
# entity-core-go

Read **AGENTS-STANDARD.md** first (ecosystem conventions). This file adds entity-core-go specifics.

## Overview

Go implementation of the Entity Core Protocol v7 — the third ground-up reference implementation (after Python and Rust), and the SDK prototype: **Go leads on new features**, cross-impl convergence is downstream feedback, not a gate.

## How we work here — tier **CORE**

This repo runs the entity-OS methodology at the **Core** tier — the framework is
`METHODOLOGY.md` (injected, identical everywhere; read it once). Conformance gates the wire
here. It does **not** catch process drift, stale build-state claims, unaccounted accumulation,
or a discipline quietly eaten by a competing legitimate pressure. Those need the ratchet.

**This repo diagnosed the reason the tier exists.** `docs/reviews/2026-08-12-discipline-audit-are-we-still-following-our-own-rules.md`
found the rules living in a sibling's guide, an ADR in a third repo, and this file — and named
the consequence: *"An audit should not have to assemble its own standard first. That is
plausibly the root cause of drift being invisible."* It also found the mechanism, which is the
part worth carrying: *"A legitimate pressure ate a discipline, and nothing in the process
noticed."* Reducing cross-repo round trips is a real constraint; it cannibalised *spec
arbitrates ambiguity, do not vote* because both point at the same act.

What binds today:

- **Universal disciplines D1–D12** (`METHODOLOGY.md` §4) — apply as written; nothing to re-derive.
- **The review questions** (§6) — run on every diff.
- **The Audit Doctrine A0–A12** (§7.2) — open it for *"Y is broken"* or *"something feels
  wrong,"* including when the thing that feels wrong is our own process. **A1 is the prime:
  trace a value before you theorize.**
- **The ratchet** — every audit ends by syncing what it taught into this file, same session.
  **If it didn't land here, it didn't land.**
- **The promotion ladder** (§3) — bit us once → an anti-pattern entry; a second time in a
  different shape → a ratified discipline. Candidates are applied, not yet claimed to generalize.
- **The divergence rule, as a standing discipline.** When a cross-impl divergence is measured,
  the response is chosen from `GUIDE-CONFORMANCE` §4's table **before** a fix is written, and
  the row is named in the commit. **A fix whose justification includes a count of
  implementations is the smell.** All-three-differ = spec ambiguity, tighten the spec; two-and-two
  = spec arbitrates, do not vote.

**The close-out ratchet does not owe a NEW rule every time — reaching for one is itself the
anti-pattern** (earned 2026-08-16 by an audit of this session's own ratchets). The E-1 close-out
minted a "path helper must reference the owner's exported path function" invariant from
`encTierCCertPath` restating a literal. Traced (A1): the literal was byte-identical to
`identity.PublicCertPath`, it never diverged, no peer corrected it, and it only re-stated §8.4.2 /
D12 one layer down — **no bite, so below even the anti-pattern floor** ("bit us once"). It was sought
out to satisfy the ritual that a feature ends with a ratchet, and it diluted the load-bearing
protocol-invariants list; removed. The rule this earns: **a close-out whose feature only re-applied
existing disciplines closes out by recording that ("no new discipline earned"), not by minting a
novel one.** Enforcement: every ratchet addition names its bite — the incident, the peer correction,
or the `(file, commit)` where it manifested; an addition that can only cite "noticed while
implementing" is a candidate at most, and usually already covered. Audit ratchet additions against
the promotion ladder, not against the calendar.

**Owed** (from the 2026-08-12 audit, promoted here so it stops being invisible): a standing
`DISCIPLINE-*` doc assembling this repo's own rules with an anti-pattern catalog; G-7, the
re-verification of the 20 build-state assertions in `cmd/peer-manager` flag help pinned to 18
stale sibling commits; and the five domains its §5 named as unaudited (§2.4a negative halves ·
§5.2/§5.2a label correctness · the ~25 dated ROUTING/HANDOFF docs for the same stale-claim
defect class applied to prose · whether the volume of cross-repo routing is itself a process
defect).

- **A new MUST-REFUSE on a data shape ripples to every PRODUCER of that shape — the oracle and the harness included, and `go test` alone will not catch it (earned 2026-08-18, CAP D11/D12).** Landing "reject a policy with null default_ttl" broke, silently, three producers of the now-invalid shape that the unit suite is blind to: the `registry_issuer` conformance checks that seed `{Mode: Open}` with no ttl (they'd have gone RED against an armed peer), `set_issuer_policy_replaces_whole` (it *asserted* the field could be cleared — now forbidden), and `validate-complete.sh`'s `--issuer-policy-mode open` arming with no `--issuer-policy-default-ttl` (the armed registry would fail its own register vectors at D12). This is the sibling of "enumerate every surface a rule names" on a different axis: a refusal rule's blast radius is every place that MINTS or SEEDS the refused shape — impl mint paths, test fixtures, **the oracle's own positive-path checks, and the peer-arming flags** — plus a matching negative conformance check. Enforcement: when you add a refuse-this-shape rule, `git grep` every constructor of the shape (here `IssuerPolicyData{`, the arming flags, `setIssuerPolicy`), and run the live category against an armed peer — a green `go test` is not evidence the wire suite still passes.

(2) The sweep was scoped to the *same-session* shape (D11/D12 policy) and never re-run against the **prior-session** refuse-rule in the same family (d948b4f F2/D3 binding), which had the identical blast radius unswept. The completed rule: a refuse-this-shape sweep's producer set includes **every generator that MINTS the shape for conformance, the fixture generators included** (`git grep` the shape's constructor across `cmd/*fixtures*` too, not just impl + harness), and landing a *new* refuse-rule obliges re-sweeping **every prior refuse-rule on a related shape** — a refusal family's producers accumulate across sessions. **Enforcement, hard: a close-out that claims "green" MUST have run `scripts/validate-complete.sh` to exit 0 and say so — `go test` green is not the release gate, and a close-out that names "full suite green" without naming the suite is how two gate failures (this fixture blocker AND pass-0b register drift) shipped under one.** (This is ADR-0012 green≠release, with the specific bite that the gate lives in a `main` self-verify and a static register pass, neither of which the unit runner touches.)
  > **Sharpened 2026-08-22 — read the gate's exit FROM the gate, never through a pipe: `validate-complete.sh | tail` returns TAIL's 0 and masks the gate's own exit 1 (earned; a prior close-out shipped on the masked form).** The rule above says a close-out claiming "green" MUST run `validate-complete.sh` to exit 0 — but running it as `./scripts/validate-complete.sh 2>&1 | tail` reports `[exited with code 0]` from **tail**, not the script, because a bash pipeline without `pipefail` takes the last command's status. Line 532 of the script exits 0 only if all six `RC*` are 0; the human-readable tell is its own summary line — `PASS 0 exit 0 · … · PASS 1 exit 1 · …` — where **any nonzero `PASS k exit` means the gate FAILED**, whatever a piped `[exited with code 0]` says. This bit twice: this session's first run printed `[exited with code 0]` over a real exit 1, and the immediately-prior go close-out claimed *"exit 0 on all six passes"* while the transcript's own summary read `PASS 1 exit 1` — the masked exit shipped as a green sign-off. **Enforcement: run the gate UNPIPED to a file and read `$?` (`./scripts/validate-complete.sh >log 2>&1; echo $?`), or `set -o pipefail`; and a close-out that quotes "exit 0" must quote the six per-pass `exit N` values, not a pipeline's status.** Same family as "presence is not validity" (a green `plan` that made no call) — here a green *exit* that was never the gate's. The nonzero this session was itself instructive but NOT a code defect: the six `peer_issued` FAILs were a sibling's leftover peer squatting `PI_PORT` 9401 (core-py's documented hazard — re-run with `PI_PORT=<free>`), a cross-session environmental collision, not a go regression; re-run clean on 9411. **No new discipline in the C-1..C-4 corpus work itself** — the de-version fold RE-APPLIED the standing "a Skip-on-missing-file guard is only a guard if its path is live" rule (the PASS 0 `[ -d …/v767 ]` guard and `corpus.Check()`'s `ErrAbsent` both went quiet, exactly as predicted, when arch deleted `v767/`), recorded per the close-out floor; the only rule earned is the pipe-masks-exit one above.
  > **Completion on the CHECK axis (2026-08-19, §4.3 set-resolver-config close-out — no new discipline, recorded per the floor).** The producer-sweep rule above is written for a refuse-*shape*; the same blast-radius holds one axis over, for landing a new *validate-peer check*. Adding `v15_dispatch_config_refused` / `v16_ttl_ceiling_reread` was `go test`-green and `validate-peer -category registry`-green, and STILL failed the gate at **pass 0b** — the static conformance-register (`cmd/conformance-register/baseline.json`) flags any check whose citation is newly unresolved, and a new check is by definition newly-present. So a new check's producer surfaces are: the **type-count guards** (`core/types/types_test.go`) when it adds a type, and the **conformance-register baseline** (re-pin with `go run ./cmd/conformance-register -write-baseline` once the citation is confirmed grounded) — both static gates a green `go test` and even a green single-category `validate-peer` run do not touch. This is the same "name the suite, run `validate-complete.sh` to exit 0" enforcement, with the bite that the two gates a new check trips are **passes 0 and 0b**, upstream of any peer.
- **Tightening a shared MATCHER/predicate ripples to every GRANT authored against its loose semantics — the same blast-radius discipline, one axis over from data-shape refusals (earned 2026-08-18 (o), the §5.4 self-match).** Removing `MatchesPattern`'s bare-prefix self-match (`X/*` no longer matches bare `X`, restoring canonical §5.4) was a *correctness* fix on one function, but authorization is CHECKED through that function, so it silently invalidated every capability grant whose scope relied on the loose match. It 403'd `maintain-peer`/`status`/`reconnect` because `ext/network`'s handler grant listed `system/network/*` as its resource and depended on that covering the BARE `system/network` the ops actually target — seven tests red in a package the matcher fix never mentions. The producer-set of a data-shape refusal is "every place that MINTS the shape" (the rule above); the producer-set of a matcher-tightening is **every grant, default-connection-grant, and scope config whose include/exclude patterns were written against the OLD behavior**. Enforcement: when you tighten a shared matcher/canonicalizer/predicate, `git grep` the grant constructors (`CapabilityScope{`, `Resources:`, `Handlers:`, default-grant builders) for patterns that lean on the loosened case, and run the FULL suite — the authorization tests that move live nowhere near the matcher's own package. The tell you got it right: rust/py already carried the tight matcher, so their grants already list the bare path explicitly — a cross-impl divergence in the *permissive* direction is a grant you are about to have to make explicit. (max_ttl this same session was the sibling data-shape case and re-applied the existing D11/D12 sweep verbatim — no new discipline there; and the published-root peer-id-segment fix re-applied the double-qualify D12 + "shared writer/reader helper passes Go-on-Go deceptively, the cross-impl FAIL is the true signal" disciplines — **no new discipline earned on either**, recorded per the close-out floor.)
  > **Inverse axis, 2026-08-23 (candidate — rust caught it in their tree, and go had the identical defect): making a check READ a field it never read before turns every existing SPELLING of that field from documentation into an enforcement input, and a spelling that is harmless as prose can be wrong as a ceiling.** (o) above is "the matcher changed, so grants written against the old semantics broke." This is the other direction: the matcher did not move — `49d4a03` (§5.2 Dimension 3 binds in-process sub-dispatch) simply added `Resource:` to the `ExecuteData` literal `makeLocalExecute` hands `CheckPermission`, and **`CheckResourceScope` began reading the `Resources` field of the §6.9 default per-handler self-grant, which until that commit nothing had ever read.** §6.9 describes that default as "all resources" and `createHandlerGrants` encoded it as bare `"*"` — but §5.5/PR-8 `capability.Canonicalize` resolves a bare `*` in a cap RESOURCE to `/{granter}/*`, i.e. **own namespace only**, so a default-scope handler could no longer write the foreign-namespace subtrees its own store legitimately holds under V7 §1.4 (Category A — a `follow` mirror at `/{them}/app/...`, a cached foreign content site). Measured, not reasoned: ceiling `["*"]` → `/2K8tBrDD.../*`, target `/2KJSNFpW.../app/test/...`, `IsCoveredBy` false, `403 capability_denied` on `system/tree:put`, while the identical binding through the bootstrap `LocationIndex` path succeeded — **the control is what makes the 403 attributable to the authorization encoding rather than to the store** (carry-the-teeth, ADR-0012). Two enforcement points. **(1) When you make a check consult a field it did not consult before, `git grep` every PRODUCER of that field and re-read each spelling as an enforcement input, not as a description** — the type change forced no call site here, so nothing pointed at the producers. **(2) Before writing a fresh encoding of a scope field, grep the same file for an existing correct one:** `createSeedPolicyEntries`'s §6.9a self-owner entry has carried the dual form `{"*", "/*/*"}` since v0.8.0, ~160 lines away in `core/peer/peer.go`, and the default self-grant never inherited it — the same sentence rust wrote about their own `debug_open_grants` R-5 note. Fixed: `defaultHandlerSelfGrant()` (peer-wildcard `/*/*`), teeth `core/peer/handler_grant_ceiling_test.go` — mutation A (restore bare `*`) reds the foreign-namespace row alone, mutation B (neuter D1's `Resource:`) reds both narrow-deputy controls, so "widening the default" and "putting a hole in D1" are pinned in opposite directions. **Peers is deliberately NOT widened**: §5.2 Dimension 4's absent→`{include:[local]}` is *correct* for a self-grant (the peer under test is `extract_peer` of the dispatch TARGET, not the namespace being written), so "completing" the fix there is an escalation, and a test says so.
- **A bare `validate-peer` run is NOT the release gate — surface-gated categories FAIL as peer-POSTURE artifacts, not defects (learned 2026-08-18, cost a chunk of a session).** `registry_issuer` returns `501 unsupported_operation` and `serving_mode` returns `404` against a peer started with a plain `peer-manager start`, because those categories require the peer to be started IN a posture (an armed issuer policy; a converged closure/namespace serving root). The release gate is `scripts/validate-complete.sh`, which starts the peer with every surface armed and scores each posture-gated category in its OWN pass (registry_issuer 31/31 in pass 3 as of 2bd2380 — the v1.11 TTL-ceiling vectors added three, serving_mode 55/55 in pass 2). **Before routing a raw-run FAIL as a sibling's — or our own — conformance defect, classify it against peer posture: a category that needs a startup flag the bare run didn't pass is an unwired surface, and its FAIL/501/404 is the artifact of that, provable by re-running under `validate-complete.sh` (or a targeted repro with a settle).** Same family as ADR-0012 green≠correct, inverted: red≠defect when the harness never armed the surface. (I nearly filed go's own `registry_issuer` 501s and `serving_mode` 404s as regressions; both were posture/timing, the peer was conformant.)
- **Diagnostics first** (`docs/architecture/guides/USING-DIAGNOSTICS.md`): when something fails, reach for `validate-peer -category $CAT -verbose 2>trace.log` + the peers' `~/.entity/logs/{name}.log` **before** reading code or writing analysis. Wire evidence is upstream of theory. Never `-verbose` the full suite to a TTY (~130 MB) — always narrow with `-category` first. For in-process Go work, use `peer.WithDispatchHook` / `WithWireHook` / `WithBindingHook` for tap observability without rebuild churn. (Negative-path tests like `security`/`multisig.escalation_*` legitimately emit 403s in the responder log — map `request_id` → test name.)
- **Never ad-hoc-filter validate-peer output.** Use `-failures-only`, `-exclude`, `-category`, `-json` — never a throwaway `python3 -c` / shell script to tally or "confirm" the tool's own output. The summary table already gives per-category P/W/F counts; to compare peers, run it N times and read the tables. (Corrected repeatedly — don't reach for `json.load` to re-verify what `-failures-only` already shows.)
- **A conditional assertion inside a check can silently no-op, and the summary PASS row cannot tell you it ran (ratified 2026-08-17 — a peer corrected around it).** `request_ttl_zero_and_overflow`'s no-ceiling probe fires only when the connection cap is nil-expiry, and the CAP-6 `ingest_rejects_unrepresentable_expiry` control runs only if the round-tripped normal-expiry token is honored — a skipped branch and an exercised one both print `PASS`. core-rust, validating the `(u)` check, *"checked the check's own message rather than the PASS row"* to see whether the branch ran, and said so. **Enforcement, both halves: (1) a conditional probe MUST report in its own PASS message whether the conditional branch executed** (as these two do: `"; no-ceiling overflow minted NO expiry…"`, and the control's honored-first gate that otherwise `SkipCheck`s), so a no-op degrades to a visible SKIP, never a silent PASS; **(2) verifying a check against a sibling, read the per-check MESSAGE, not the summary PASS/row-count.** Same family as ADR-0012 (green ≠ correct if the assertion didn't fire).
- **When an oracle check cannot be teeth-tested against a failing peer, carry the teeth IN the check (2026-08-17).** The usual proof — run the check against a pre-fix commit and watch it go RED — is blocked when no failing peer is buildable: go never had the defect, and the git boundary forbids checking out a sibling's pre-fix commit (`entity-core-{py,rust}`). The CAP-6 ingest check instead embeds a **negative control**: a round-tripped *normal*-expiry token must be **honored first**, proving the construction reaches the expiry check, so a refusal of the hostile variants is attributable to the expiry rather than to a corrupted granter/chain; if the control is refused the check **SKIPs, not PASSes**. A hostile-input check whose valid-input control is never asserted is a candidate false-pass. (This is ADR-0012's mutation-has-teeth applied to a wire check — not a new invariant, a new place to apply it.)

## Versioning — our number is ours ([ADR-0002])

**Canonical statement + the reasoning: `CHANGELOG.md` §Versioning.** Enforced by
`cmd/internal/hygiene/version_test.go`. The short form:

- **`0.y.z` is this repo's own 3-field SemVer**, forward-only from the published
  `v0.8.0`. **`v7.NN` is the protocol revision we implement** and rides out-of-band.
  **`N · 0F · 0S · 0W @ <commit>`** is what we measured. Three numbers, three jobs —
  ADR-0002 separated them on purpose, and conflating them is the failure it names.
- **Never adopt a sibling's release number.** `entity-core-protocol`'s `0.8.x` is the
  *spec repo's* version. The fleet shares a cut **date**, not a **number**, and the
  numbers are expected to diverge. This is not theoretical: on 2026-08-23 a
  coordination pass wrote `## [0.8.2]` — the protocol's number — into our CHANGELOG,
  and nothing in the tree contradicted it because nothing in the tree had ever said
  what our number was. **A convention that is not written down gets decided by
  whoever asks last.**
- **A cut is ONE edit across every declaration site** — the CHANGELOG heading,
  `ext/go.mod`, `cmd/go.mod`, README §Module paths. The trap is go-specific and
  silent: a sibling-path `replace` hides a stale `require` from *us* and from nobody
  else, because a consumer resolving `.../cmd@vX` gets the requires **without** the
  replaces. A `cmd` cut that still requires the previous `core` publishes a build
  reproducible only inside this workspace. `TestModuleRequiresMatchTheLatestRelease`
  is the gate; it goes RED the moment a release heading lands unaccompanied.

## Citations on the PUBLISHED surface: name the finding, not the hash

**Earned 2026-08-23, browser-rust caught it downstream.** `core/peer/peer.go` and
`core/peer/handler_grant_ceiling_test.go` both cited `entity-core-rust`'s fix as
`c484fa6` — a commit that exists **on no branch, in no repo**. The rust seat had
committed, reset `dev` locally, and re-committed, twice; `c484fa6` survives only in
that machine's reflog. Nothing was lost (the trees are byte-identical to the surviving
commits and the remote only ever moved forward) but the hash a reader looks up resolves
nowhere. Both files are `.go`, so both **ship**.

The rule is [RUNBOOK-RELEASE-CURATION] + [ADR-0012] Amendment 1 and it is stronger than
the orphan case: `--series` **re-authors every commit** on the release branch, so an
internal SHA quoted in a file that publishes can never resolve for a public reader *even
when it is perfectly alive here*. A sibling's SHA is worse — the reader has no such repo.
**In anything that ships, cite the SYMBOL and the finding** (`their
default_handler_self_grant`, `core/capability/src/lib.rs`) — that is what
AGENTS-STANDARD's *"pin citations to `(symbol, path, commit)`"* reduces to when the
commit half cannot travel. A released version or a tag survives a re-author; a dev SHA
does not.

**Two kinds of SHA live on our published surface and they are NOT the same** — the
distinction is what to check before touching one:

- **A POINTER** — "fixed at `abc1234`", "landed at rust `3e9c9fc`" — invites the reader
  to go look. On the published surface it is broken by construction. Rewrite it to name
  the symbol/behavior; keep a hash only if it is a *tag* or a released version.
- **A RECEIPT** — `cmd/peer-manager/start.go`'s `siblingPinRust` / `siblingPinPython`,
  the corpus artifact hashes, `docs/STATUS.md`'s `@ <commit>` measurement pins. These
  do not ask to be resolved; they record *the state a claim was verified against*, and
  ADR-0012 **requires** them ("a number is only true of the commit it was taken at").
  Leave them. Stripping a receipt would delete the only thing that dates the claim.

**Enforcement, before you write one:** ask whether a reader of the published mirror is
expected to *resolve* it. If yes, it is a pointer and the hash is the wrong citation. If
it is a receipt, say so at the site (`[historical]`, `read live <date>`, `measured @`) so
the next sweep does not "fix" it. The measured scope on the published tree today is ~161
distinct hashes across ~115 files, overwhelmingly receipts; the two above were the only
pointers to a commit that resolves nowhere at all.

Teeth: `ext/compute/depth_constraint_test.go` (grant-level `max_compute_depth` lowers the budget through `initBudget`; mutation = strip the constraint, default stands) + the go-on-go wire LOCK; the §5.2 pseudocode that misled the read (`capability.data.constraints`) is routed as spec-issue `2026-08-22-a` so rust/py don't inherit the same silence — the cross-impl re-drive of the 362 corpus is the confirmation that owes.

- **Don't defer on "implementation-defined" or "Rust/Python don't have it yet."** We are the impl team — implementation-defined means *we* define it; multi-Go-peer validation is real validation; cross-impl is downstream feedback.

## Verify build state before you assert it — READ THE LIVE WORKTREE

**"Filed, not yours" is about provenance, not ownership — a normative change to a definition site we
bind against is owed work no matter which section announces it (earned 2026-08-18 (m), arch caught it).**
We acknowledged arch's `-i` ask to confirm "any doublestar dependency removed" and it was **false**:
go carried the §4.6 `type_pattern` doublestar matcher (`ext/type/constraint/globMatch`) the whole time,
and we confirmed "removed" without opening it — because `-i` filed the §4.6 fold under a heading
("Arch-owed, filed, not yours") that told three engine seats the change was not theirs. It was *their
defect to fix* (provenance) but a definition site *we implement a matcher against* (ownership of the
follow-on), and all three of us confirmed removal of a dependency we all still had. Our own spec-issue
then reasoned from the pre-fold §4.6 text, two commits stale. **The rule: when a fold/ruling touches
spec text this repo implements a matcher / encoder / validator / canonicalizer against, open THAT
surface and re-read our code before acknowledging anything about it — regardless of whether the packet
files it as ours.** Enforcement: an acknowledgement of "removed / changed / conformant on X" names the
`(file, symbol)` it checked (here `ext/type/constraint/handler.go` `globMatch`), never a bare "confirmed";
a §-heading that says "not yours" is not evidence about our tree, only about whose defect it was. Same
family as the sibling-negative miss — the sentence nobody opens the tree for is the one that ships wrong.

Any claim about what another repo *has built* — a flag it honors, a surface it lacks, a seam that
is unbuilt — is a **build-state claim**, and it decays the moment that repo commits. Before making
one:

- **Open the tree.** `git status` + HEAD + **read the actual source**. A report, a handoff, or
  `git log` alone is not sufficient; run `git log --since` on every sibling the claim touches.
- **Cite `(repo, commit, date)` at the point of the claim**, not in a preamble.
- **Never carry a dated measurement across a commit change.** If the target moved, re-measure or
  re-pin — a number is only true of the commit it was taken at (ADR-0012).
- **A peer's correction outranks our inference, immediately.** They can read their own tree.

**The shape, so it is recognizable:** a stale build-state claim is always *plausible* — it was
true when written and reads fine forever after. Review does not catch it; only opening the tree
does. It has been caught four times, every time by a peer, never by us re-reading our own text.

**It fails in both directions.** A capability note can be wrong by being **ahead** of reality as
easily as behind it — `--publish-root` once asserted republish-on-change as though the spec
required it, when no landed spec obliges a publisher to republish at all. "Rust + Python pending"
outlived the gap it described; "honored by all three" preceded the rule it implied. Both are the
same defect, and both read as a sibling bug that isn't there.

This applies hardest to **`cmd/peer-manager` flag help**, which is where these claims accumulate:
every `Honored by …` / `… impl pending` string is a build-state assertion about a repo we do not
control. Re-verify them whenever a sibling moves, and treat a stale one as a defect, not a typo —
it is the documentation of a skip.

**RATIFIED 2026-08-15 (f) — the sentence about the sibling is the one nobody verifies.** This has
now bitten **twice in two sessions**, both from a grep miss on a *sibling's* tree: the "both

A grep that finds nothing is not evidence of absence; it is evidence your pattern missed. The
enforcement point: before a report asserts a sibling lacks something, `git grep` the sibling for the

## Cross-impl validation deliverable

When validating Python/Rust against a spec change, the deliverable is a **written per-peer report under `docs/validation/reports/`** (dated filename, matching prior reports: headline pass/partial/blocked, category table, each gap with spec requirement + probed request shape + peer response + why it matters + suggested fix/test, repro steps) — not chat output that evaporates. Run the validator, report what you observed, and stop: don't dig through the sibling's git history or internals to root-cause — that's a separate job.
